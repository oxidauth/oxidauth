## Problem

`State` stores the current credential twice — as a decoded `Jwt` (`state.jwt`) and as the raw wire string (`state.raw_jwt`) — and keeps them in sync only in one of the two places that advance the token. `auth()` writes both; `refresh()` writes only the decoded copy. Result: after any successful refresh (manual `client.refresh()` or the automatic `check_auth_state → AuthState::Refresh → refresh()` inside `get_jwt()` / `get_jwt_decoded()` / `request()`), `get_jwt()` — the SDK's headline public-string accessor — returns the pre-refresh token string, which by definition is expired (`check_auth_state` only reaches `Refresh` when `now > jwt.exp`). The register line is accurate about the mechanism; the only correction is that it does not propagate to the wire header, so this is an accessor-corruption bug, not a total-refresh-failure bug.

The authors pinned the wrong behavior in two tests rather than fixing it (`BUG(pinned)` at `mod.rs:966-968`, plus the unlabeled pin comment + assertion at `mod.rs:1341-1345`), so today's test suite actively asserts the stale return.

## Analysis

**Invariant that exists in `auth()` and is violated in `refresh()`:** `raw_jwt` is (meant to be) the exact string of the validated `state.jwt`. In `auth()` the same `payload.jwt` feeds `raw_jwt` (274), the decode check (270), and the bearer header (278). In `refresh()` the same `payload.jwt` feeds the decode loop (377) and the bearer header (389) — but not `raw_jwt`. Post-refresh, `State` therefore describes two different sessions simultaneously: header + decoded = token N+1, `raw_jwt` = token N.

**Who consumes `get_jwt()` and breaks:** any code that takes the raw string out of the SDK — forwarding a bearer to a third-party service, stamping outbound webhooks, building an `Authorization` header by hand, debug/logging, or anything that caches "the token" as a string. `get_jwt()` returns `Ok(stale)` with zero staleness signal, so failures (`401 invalid signature`/`jwt expired` downstream, sometimes intermittently — a just-expired token still passes verifiers with clock leeway, masking the cause until it ages out) surface far from the SDK. A subtler failure: cross-checking `get_jwt()` against `get_jwt_decoded()` (e.g. validating `exp` locally before sending the string elsewhere) sees a token whose decoded expiry disagrees with what the client just reported as current.

**Edge cases / audit of every `raw_jwt` writer↔reader pair:**
- `auth()` writer vs `get_jwt()` reader: consistent (same string) — the *only* consistent pair today.
- `refresh()` vs `get_jwt()`: the bug.
- Failed auth leaves `raw_jwt` `None` → `get_jwt()` → `NoJwtFound` (pinned correctly by `authenticate_rejects_jwt_signed_with_foreign_key`, `mod.rs:904-927`); the fix must not disturb this: the `raw_jwt` write stays inside the *validated* (`Some(jwt)`) arm, so a rejected token is never stored raw — same ordering as `auth()` (decode first at 270, store at 274).
- Rotation across consecutive refreshes (`refresh_rotation_persists_rotated_token_for_next_refresh`, 979–1033) exercises `refresh_token` rotation only; `raw_jwt` desyncs by one generation per refresh, compounding: after N refreshes `get_jwt()` serves token 1's… predecessor — the original auth-time string, since nothing else ever overwrote it.
- Concurrency: `refresh()` holds the `state` write lock across its whole keys+refresh exchange (comment at 1303–1307); queued `get_jwt()` callers re-read fresh state and today *all* receive the same stale string (`concurrent_get_jwt_after_expiry_refreshes_exactly_once`, 1309–1354, asserts `stale_jwt` at 1344). Post-fix, all receive the fresh string — no new races; adding the write is inside the same critical section.
- **Production gating (fix ordering):** CLI-3 means `refresh()` currently can never complete against a live server (every served key fails its base64 decode → `"failed to validate jwt"`, pinned at `mod.rs:1290-1300`), so CLI-2 is unreachable in production until CLI-3 lands — and then becomes immediately visible. The two fixes interact: fix both together or land CLI-3 first with eyes open.
- **Root cause in one sentence:** duplicated source-of-truth fields (`jwt` + `raw_jwt`) with no type enforcing co-write.

## Impact

- **SDK consumers (primary):** every platform (native + wasm) — anyone extracting the token string via `get_jwt()` after an auto- or manual refresh ships a stale/expired bearer to third parties while their own API calls work (because `request()` uses the rebuilt header client). The asymmetry makes it maddening to diagnose: "the client refreshed fine (`get_jwt_decoded()` is fresh, my requests pass) but the token I forwarded is rejected."
- **Server/API:** unaffected — the wire header is correct; no server endpoint ever sees the stale string via this crate.
- **Public API compatibility:** none of the fix touches signatures — `get_jwt()`, `refresh()`, `ClientTrait` unchanged. Only the *returned value* changes, which is the bug fix. Consumers who pinned tests to wiremock in exactly the way this repo did (asserting the stale string) will see flips; that is the pin flip below.
- **Severity P1 stands** (with the CLI-3 gating caveat): the broken path is the SDK's primary documented token accessor, on every client with tokens that expire — i.e., all of them.

## Proposed resolution

1. **The fix (one write, in the validated arm of `refresh()`, `oxidauth-rs/src/client/mod.rs:384-387`):** bind the response string once and feed all three sinks — e.g. `let new_jwt = payload.jwt;` after the decode loop, then inside `Some(jwt) => { ... }`: `state.raw_jwt = Some(new_jwt.clone());` (or move it into `raw_jwt` and format the bearer at 389 from the stored value / an `as_deref()`) alongside the existing `state.jwt = Some(jwt);` / `state.refresh_token = Some(payload.refresh_token);`. Keep it *after* successful decode so the "only validated tokens are stored" invariant (and the `NoJwtFound`-on-rejected-auth behavior) is preserved.
2. **Pin flips (both required to compile-green):**
   - `oxidauth-rs/src/client/mod.rs:966-969` — delete the `BUG(pinned)` comment; flip `assert_eq!(returned, stale_jwt);` → `assert_eq!(returned, fresh_jwt);` (`fresh_jwt` is already bound at 941). The adjacent assertions (`get_jwt_decoded().exp == fresh_exp` at 972, "no further HTTP" at 975) already describe fixed behavior and stay.
   - `oxidauth-rs/src/client/mod.rs:1341-1345` (`concurrent_get_jwt_after_expiry_refreshes_exactly_once`) — rewrite the "consistent with the stale-raw_jwt pin" comment; flip the loop assertion `assert_eq!(r.unwrap(), stale_jwt);` → `assert_eq!(r.unwrap(), fresh_jwt);` (`fresh_jwt` bound at 1317). The concurrency invariants (exactly one refresh POST, exactly two keys fetches) are unrelated and MUST NOT move.
   - Untouched neighbors, explicitly: the `BUG(pinned)` at 1074 (CLI-4) and at 1290 (CLI-3 / PEM-format pin — `refresh_is_broken_against_the_real_raw_pem_wire_format` will keep asserting the *base64-decode* failure and is a separate fix; if both land, that test should be reworked into a positive refresh test in CLI-3's ticket, not here).
3. **Structural hardening (recommended, same PR if cheap):** collapse the duplicated credential into one field so the desync is unrepresentable — e.g. `token: Option<StoredJwt>` with `struct StoredJwt { raw: String, decoded: Jwt }` (constructor `StoredJwt::decode_with_public_keys(raw, keys)?` populates both; `get_jwt()` returns `.raw.clone()`, `get_jwt_decoded()` returns `.decoded.clone()`). This deletes `raw_jwt` from the public-ish `State` (it is `pub struct State` with private fields — the removal is not a semver-visible API change for method callers, but confirm no external code constructs `State` directly; `State` derives `Default` and is only built in `Client::new`/`test_client` in-crate). If taken, this also resolves the audit requirement by construction: the only writers become `auth()` and `refresh()`, each constructing the whole pair.
4. **Regression test (new, in the same test module):** after `authenticate` + an expiry-driven `get_jwt()` refresh, assert the invariant the fix restores — (a) `client.get_jwt()` equals the fresh response string, (b) the `Authorization` header actually sent on a subsequent `request()` equals `Bearer <client.get_jwt()>` (wiremock `received(...)` inspection) — pinning that accessor and wire can never diverge again.
5. **Out of scope:** CLI-3 (PEM decode in `refresh()`), CLI-4 (`Other("")` error arm), CLI-10 (`get_version` hardcode) [CLI-10/OXA-000036 SUPERSEDED 2026-09-30 — phantoms: get_version/build_authorization never existed in SDK history (verified by full git-history grep); OXA-000036 closed as note.] — separate register items in the same file; cross-reference at implementation time.
