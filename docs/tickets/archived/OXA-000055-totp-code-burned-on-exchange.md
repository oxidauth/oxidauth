## Problem

N-5 asserts the opposite of what the code does. Its premise — "`validate()` consumes the code, so a failed exchange step forces a fresh code" — describes an API boringauth 0.9.0 does not have and a consumption state oxidauth never stores. What actually happens:

1. `validate_totp` checks the code with a **stateless, per-request** `is_valid` (`validate.rs:112-118`). A true code is never marked as seen, before or after the rest of the exchange.
2. If any later step fails (private-key fetch/decode, permission tree, refresh insert, JWT build/encode — the register's "refresh-rejected" is the `:169-175` insert), the caller gets a 400, **and the same code still validates on retry** until the current `totp_ttl` bucket rolls.
3. Consequently there is **no forced-fresh-code UX** to document — and equally, the note's parenthetical "Intentional (no replay)" is an intent the implementation does not provide. The real behavior is: **one code per bucket, replayable any number of times within the bucket's remaining seconds** (0…`totp_ttl`; test-pinned at 600s, production = authority `totp_ttl` setting).

The ±1-step cross-link (N-7, "`totp::validate` tests" pin "±1 step / 60s drift window") is also inverted: boringauth defaults both tolerances to **zero** (`totp.rs:203-204`), oxidauth never widens them, and the tests' `stay_inside_totp_window` helper exists *because* zero tolerance makes boundary-straddling attempts fail. There is no ±1 acceptance and no "60s window" — the acceptance window is just the remainder of the current bucket.

## Analysis

**Where consumption would have to live, and why none of it does.** Code burning requires verifier-side state: either a boringauth API that mutates the TOTP object (it has none — `is_valid` is `&self`, and the object is dropped after one call anyway) or an application-level "last accepted step" record (RFC 6238 §5.2's replay countermeasure). `TOTPSecret` stores only the secret; no table, struct field, or cache tracks used steps; no test ever submits a code twice. So both the mechanism and the observable pin of "burned" are absent.

**Would a retry inside the window re-accept?** Yes — and this is the only correct answer to the note's scenario, because nothing burns. A retry after a failed JWT mint or refresh insert re-accepts the same code as long as `epoch()` is still in the same bucket; the first failure mode on a late retry is the ordinary `"invalid totp code"` (`:121`) after the bucket rolls. Contrast with TOTP-standard deployments: most verifiers (RFC 6238) also leave codes replayable within the window unless they add last-step tracking, and many accept ±1 step; oxidauth is the *narrower* variant (zero tolerance) of the *same* no-consumption default. N-5 described neither.

**Do any test pins block changing this?** No pin asserts burn (no double-submit exists anywhere), and no pin asserts ±1 either — the pins (`validate.rs:487`, `update_password.rs:451`, `forgot_password.rs:224`) all document zero tolerance and would only need comment updates if ±1 tolerance were ever added; the `stay_inside_totp_window` helper would become unnecessary but stays harmless. So the register's stated intent ("no replay") could be implemented as burn-on-success without flipping any existing assertion; conversely, keeping current behavior requires no test changes either.

**Security assessment of the actual (non-burned) state.** For `totp/validate` specifically, exposure is bounded: minting a session requires *both* the code (delivered out-of-band via webhook) and a scoped 2FA JWT that only a successful username/password authentication produces (`authenticate.rs:165-173`). The residual replay vector is same-bucket double-exchange by someone who has both artifacts — low-value, short-window. The materially worse sibling is `update_password.rs:121-131`: a reset code (`.period(600)`, i.e. up to a full 10 minutes) is accepted any number of times in its bucket — *including after a successful password change* — which amplifies the OXA-000005 leak (an unauthenticated `forgot_password` call hands out the code directly): today a leaked code is not merely live, it is multi-use until the bucket rolls. That is the honest successor of the concern N-5 was reaching for.

**Interactions with open tickets.** OXA-000005 (see above — non-consumption makes leaked codes replayable, so any burn-on-success slice should cover both call sites). OXA-000029/000030: the register's feared UX ("failed exchange forces a fresh code") would, if it were true, compound with the CLI defects — OXA-000029 means `refresh()` can never validate a served JWT even after a *successful* exchange, and OXA-000030 collapses every server failure to an empty error string, so a client could not even tell which exchange step failed. Under the *actual* semantics the user just retries the same code and (server-side) succeeds — but OXA-000030 still hides why the first attempt failed, and OXA-000029 still breaks the client after success. This is one more reason not to adopt the note's implied burn-on-attempt: with 000029/000030 unresolved, every post-check infrastructure failure would strand the code and force a full re-login + email reissue.

**The register's implicit "redesign" option is the wrong one.** Burning at check time (consume before the exchange completes) is strictly worse than the RFC's burn-on-success: it punishes infrastructure failures with code loss, needs the same last-step storage anyway, and buys coverage (failed-attempt replay) that the bounded artifacts above make marginal. boringauth offers no support for it regardless.

## Impact

None at runtime today — the UX pain N-5 describes never occurs, and no code path or test depends on consumption. The live cost is the register itself being wrong in two directions: (1) N-5's "Intentional (no replay)" invites readers to believe replay protection exists when it does not (material for the `update_password` reset code per OXA-000005); (2) the cross-referenced N-7 "±1 step / 60s window" misstates the acceptance window, which is actually zero-tolerance — meaning real users who submit a correct code in the last seconds of a bucket get `"invalid totp code"` (the same boundary straddle the test helper defends against), the opposite usability surprise from the one recorded.
