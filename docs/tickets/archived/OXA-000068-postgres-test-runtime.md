## Problem

T-8 is a conventions/perf record, not a defect. Checked clause-by-clause (register text in quotes):

1. **"all 150 DB tests" — ✓.** Exactly 150 `#[sqlx::test]` attributes in `oxidauth-postgres/src` (0 plain `#[test]`); S14's review log census (missing-tests.md:597) sums per-entity counts to exactly 150. The `bin/database_test.sh` gate number is 163 because the same script also runs 13 xlib-`postgres` tests — worth stating in the doc, since the register number alone doesn't reconcile with the suite output.
2. **"complete in ~5s" — recorded observation only, no source artifact.** The S14 log records the 150/0 run but **no wall time**, and no other pg-suite timing appears in `missing-tests.md`; `database_test.sh` sets no timeout. The figure cannot be re-measured here (tooling ticket — no test runs), so it must be cited as an observation from the register, not as repo-verified data. It is *plausible* against the cost model (Analysis) but should be flagged unmeasured — or replaced by one measured figure when the suite next runs.
3. **"(sqlx per-test transactions)" — ✗, and it misattributes the very speed it explains.** OXA-000066 disproved the transaction folklore (sqlx 0.8.6 has no transaction code path; isolation = per-test `CREATE DATABASE`), and its step 3 explicitly defers the T-8 parenthetical correction to this ticket. The ~5 s figure is *the CREATE-DATABASE-per-test runtime* — transaction isolation would have been *cheaper*, so the correct explanation for the speed is small empty per-test DBs + 18 tiny migrations + libtest default parallelism, not transactions.
4. **"`--test-threads=1` only when a future test genuinely needs ordering" — right advice, wrong premise.** With per-test databases there is no DB state an execution order can touch; ordering can never be an isolation fix here (Analysis). And the real leftover-state nuance the folklore was gesturing at — failed tests leave their database behind — is a **lifecycle** caveat, not an ordering one.

## Analysis

**What one test actually costs (verified in the pinned 0.8.6 source).** Connect to `DATABASE_URL` via dotenvy (master pool ≤20 conns, shared per binary) → `pg_advisory_xact_lock` + `_sqlx_test` schema/registry bookkeeping → `do_cleanup(same name)` → registry insert → `CREATE DATABASE "_sqlx_test_<sha512(test_path)>"` (physical copy of template1 — cheap for an empty DB) → `crate::MIGRATOR.run_direct` replays the 18 migrations on one connection (they seed no rows — the exact-`COUNT` contract OXA-000066 §4) → the test body runs on its own ≤5-connection pool, every statement committed for real → `pool.close()` bounded at 10 s (`sqlx-core :202-208`) → on success `drop database`. At a few hundred ms/test on local docker Postgres and libtest's default parallelism (= core count), 150 tests finish in seconds — the ~5 s register figure is consistent with the mechanism; keep it as the regression baseline, labeled "recorded, unmeasured".

**Corrected lifecycle — one refinement of OXA-000066's own §2 wording.** `run_test` drops the test DB only `if res.is_success()` (`sqlx-core :232`), so a failing **or panicking** test leaves its database and `_sqlx_test.databases` row behind (deliberately, for `psql` post-mortem). OXA-000066:38,63 says leftovers are "swept at startup / next run" — half right: `cleanup_test_dbs` (the would-be startup sweep, `sqlx-postgres :41-84`) is **dead code in 0.8.6** — no caller in sqlx-core, sqlx-macros, or sqlx-macros-core (the dangling comment at `:21` describes an unimplemented feature). The real reclamation is name-identity: DB names are deterministic hashes of the test path (`sqlx-core :48-56`), so a leftover dies when **that same test runs again** (`do_cleanup` before `create`). Consequences: DBs belonging to renamed/deleted test paths persist forever; disk grows with accumulated failures between re-runs; and a leftover DB is inspectable precisely because nothing rolled back.

**Is that the real "ordering" caveat? Yes, record it — but relabel it.** Nothing in the lifecycle depends on which test ran when: a leftover is only ever cleaned by *itself*, never by a neighbor. The honest rule the register should carry is: *state persists per test-name across runs (failure keeps the DB, success drops it); it is a disk-hygiene and debugging note, never a reason for `--test-threads`*.

**Why `--test-threads=1` is never needed for the DB suite (cross-check with OXA-000065).** `oxidauth-postgres` tests touch neither process env nor global subscribers (grep: zero env references; the only env access is sqlx's read-only `dotenvy::var("DATABASE_URL")` per test context) — they are parallel-safe **by design**, not by guard. OXA-000065's `ENV_LOCK` convention lives in different test binaries (`oxidauth-services`, `telemetry`, and the 4 env-mutating `xlib/postgres` `db_tests`, guarded by their own `ENV_LOCK` + `TEST_`-prefixed keys); separate binaries = separate processes, so the 163-test `bin/database_test.sh` run is parallel-safe end to end. The register's own serialization idiom is the per-crate guard, not a harness flag — so even a hypothetical genuinely order-dependent test in this crate should reach for a guard or a self-contained design, not `--test-threads=1`. The one *quantitative* parallelism risk is connection pressure, not ordering: master pool ≤20 + per-test pools ≤5 × libtest threads (default = cores) against Postgres' default `max_connections = 100` (no override in `src/oxidauth/docker-compose.yml`); S14's 150-green run on default threads shows it is fine at normal core counts; a many-core CI box with connection-heavy tests would want `--test-threads=N` as a **cap** (mechanism verified in source; the threshold is arithmetic — `[INFERENCE]`).

## Impact

- **Register integrity:** T-8's parenthetical is one of the four live folklore sites OXA-000066 enumerates; leaving it teaches the wrong mechanism at the exact place people learn "why it's fast", and every future copy of the line (docs, tickets — the pattern already spread through `000053`/`000054`) re-propagates it.
- **Regression baseline:** "150 DB tests ≈ 5 s wall" is the only runtime expectation on record for the DB gate. Kept and correctly attributed, it lets a future contributor distinguish "a slow migration landed" (linear, expected — every test replays all migrations, OXA-000001's point) from "something pathological" (pool-close 10 s timeouts, connection exhaustion). Silently dropping it loses that; attributing it to transactions makes it unfalsifiable.
- **Cargo-cult prevention:** without the corrected rationale, a future flaky-looking DB test invites `--test-threads=1` as a fix — which would serialize 150 real `CREATE DATABASE`s (the suite's headline strength becomes its worst cost) while fixing nothing, since ordering cannot cause DB interference.
- **Disk hygiene:** the unimplemented sweep means a long-lived dev box accumulates one surviving DB per failing test-run that was never re-run green (plus permanent leaks on test renames); unrecorded, that surprises people as "mystery databases" in `\l`.
