## Problem

Microsoft Graph returns `"mail": null` on `GET /me` for directory users without a mailbox — most commonly **B2B guests** in an Entra tenant. Because `MicrosoftProfile.mail` is `String`, serde rejects the *entire* profile document, `retrieve_microsoft_profile` returns `Err`, and the OAuth2 authenticate-or-register flow aborts before any identifier exists. The login dies at deserialization instead of falling back to another identifier: a legitimate, licensed Entra guest can never sign in through a Microsoft authority, and the browser gets the generic "Contact support" text (HTTP 200 today) with the real cause visible only in server logs as raw serde prose.

The register's wording is exactly right modulo the pointer: the pinned test at `:143-164` demonstrates both failure shapes — explicit `"mail": null` (`:149-156`) and the key absent entirely (`:157-163`) — and asserts both are errors.

## Analysis

**Mechanism.** `serde_json::from_value::<MicrosoftProfile>` on `{"displayName":"Guest User","id":"...","mail":null}` fails at the `mail` field ("invalid type: null, expected a string"); a missing key fails with "missing field `mail`". There is no per-field tolerance anywhere — `TryFrom<JsonValue>` (`mod.rs:42-46`) just wraps the error, and `retrieve_profile.rs:22-23` (`?` on `.json()`) forwards it untyped. One nullability mismatch on an optional display field annihilates a login whose other fields (`id`, `displayName`) were perfectly usable — the fallback the register asks for is *structurally impossible* today because the parse never completes.

**Which Graph fields null out for guests.** Fetch-verified against `https://learn.microsoft.com/en-us/graph/api/resources/user?view=graph-rest-1.0` (2026-09-29):

- `mail String ... Returned by default. Supports $filter ( ... and eq on null values)` — officially null-able, and returned by default, so it arrives as `"mail": null` rather than being omitted (the actual guest wire shape being `"mail": null` vs omitted is `[INFERENCE]` from the "eq on null values" filterability plus field-reported guest behavior; the pinned test covers both shapes anyway).
- The same page's proxy-address section: "A user's mail is NOT set to the primary proxy address if the user is a guest and the primary proxy address contains the guest's UPN string with #EXT#. A user's mail is NOT removed, even if they no longer have proxy addresses if the user is a guest" — i.e. for guests, `mail` is explicitly *not* maintained; a mailbox-less guest simply has none.
- `userPrincipalName String ... This property is required when a user is created` — always present. Guests get a `alias@domain#EXT#<tenant>.onmicrosoft.com`-shaped UPN (the `#EXT#` marker appears verbatim in the quoted docs passage), which is **not a deliverable email address**.
- `id String The unique identifier for the user. Should be treated as an opaque identifier. ... Key. Not nullable. Read-only. Returned by default.` — always present, the stable key.
- `otherMails String collection ... Requires $select to retrieve` and `businessPhones ... Requires $select` — the strategy does no `$select` on `profile_url` (`retrieve_profile.rs:13-18`), so these are absent by default; they are not viable inputs regardless of nullability.
- Scope interaction: `AuthorityParams.scopes` is operator-stored (`strategies/oauth2/mod.rs:34`); the test fixture uses `"openid email profile"` (`mod.rs:99`). The `email` scope is what surfaces the SMTP/mail property — so even a mailbox-holding user loses `mail` if the authority's stored scopes omit `email`. Null (no mailbox) and absent (no scope) are two independent routes to the same parse death.

**Identifier extraction and the fallback decision.** Today the *entire identity* of a Microsoft-login user is `profile.mail` — nothing else in `MicrosoftProfile` reaches `user_identifier` (`id` is deserialized at `:35` and then discarded by `retrieve_profile.rs:25-29`, which maps only mail/given/surname). Any fallback chain must respect two constraints:

1. **Uniqueness:** `UNIQUE (user_identifier, authority_id)` (migration `20240619063635`). Different identifier *shapes* for different users are fine — the chain just must not assign the same string to two humans within one authority.
2. **Stability across logins:** the authenticate leg re-derives the identifier from the live profile every login (`authenticate.rs:115-123`). If the chosen identifier ever *changes* for the same human (e.g. registered while `mail` was null under a UPN fallback, then a mailbox is provisioned and `mail` appears), the lookup misses, the `"user authority not found:"` branch fires (`services/authenticate_or_register.rs:197-202`), and the system **silently registers a duplicate user** for the same person. This re-key hazard is the real design constraint, and it exists for *any* email-shaped chain: `mail`-first flips a guest's key the day a mailbox appears; `userPrincipalName`-first is not safe either — guest UPNs are rewritten in some mailbox-provisioning/soft-restore flows `[INFERENCE — tenant-admin-reported behavior, not in the fetched docs page]`. Only `id` is documented-stable ("Key. Not nullable."). Microsoft's own docs make the mirrored point for Google (fetch-verified, `https://developers.google.com/identity/openid-connect/openid-connect`): the email claim "may not be unique to this account and could change over time, therefore you shouldn't use this value as the primary identifier to link to your user record."

**The fallback value is also user-visible.** `OAuth2Profile.email` does not just key the lookup — it becomes the `?email=` query parameter of the SPA handoff redirect (`callback.rs:106,132`; success-URL shape pinned at `callback.rs:331-348`) and `users.email`/`users.username` on auto-register (`services/authenticate_or_register.rs:202-208` → `registrar.rs:31`). A `#EXT#` UPN or opaque Graph id will therefore appear in the SPA and in the users table. That is cosmetic-but-real: prefer the most email-like available value, and accept that the key may not be.

**Why "better error" is still needed after a chain.** With `id` kept required, the chain always yields *something*; the residual "no identifier" case is a malformed/error body (Graph returning an error envelope, a proxy HTML page, or a body without `id` at all). Today that is raw serde prose; OXA-000010 Step 3 already owns typed per-flow errors and explicitly names `OAuth2ProfileError` as the deliverable "same shape for both `retrieve_*_profile.rs`" (`docs/tickets/OXA-000010-aor-state-replay.md`, Step 3) — this ticket's no-identifier failure should become a variant of that type (e.g. `NoIdentifier`/`InvalidResponse`), which is also what lets OXA-000037 Phase 3 map it to an honest status instead of 400-with-blame.

**Google variant comparison.** `GoogleProfile` (`google/mod.rs:27-36`) inverts the Microsoft shape: `name`/`given_name`/`family_name`/`picture`/`id` are `Option<String>`, but `email: String` + `verified_email: bool` are required (`:34-35`). A Google *account* always has an email address in practice, so a Graph-style `null` is not the realistic trigger — the realistic trigger is **scope-conditional absence**: fetch-verified from the OpenID Connect page above, the `email` claim is "Provided only if you included the `email` scope in your request" (and likewise `email_verified`). An operator whose authority params omit `email` from `scopes` hits the identical whole-profile parse death (`missing field email`, then `missing field verified_email`) on *every* Google login. `google/retrieve_profile.rs:26` likewise maps `email → OAuth2Profile.email` and discards `id` (currently `Option`, usable as the fallback if promoted). Same class, lower trigger probability; the resolution below keeps it an optional step so this ticket stays register-faithful.

**Rejected alternative — read the `id_token` instead.** The exchange response carries `id_token` (`MicrosoftExchangeTokenRes.id_token`, `mod.rs:26`; guest tokens carry `sub`/`oid`/`upn` claims even without a mailbox) but `exchange_microsoft_token` returns only `access_token` and drops the rest (`exchange_token.rs:32`). Consuming it for identity requires signature/claim validation, which is unimplemented and owned by OXA-000004; adopting it here would create an unverified-identity path. Note for OXA-000004's later resolution, do not adopt now.

## Impact

- **Who:** every tenant operating a Microsoft authority that admits B2B guests without Exchange mailboxes — the standard cross-tenant collaboration shape in Entra (partner users invited with a personal Gmail/Outlook identity are exactly the mailbox-less guests). Each such user has a real, licensed Entra account and can *never* complete SSO: a permanent, silent lockout of a whole user class. Secondarily, member accounts in tenants where the authority's `scopes` omit `email`.
- **Failure UX:** a dead-end "OAuth2 Error — unable to authenticate. Contact support for assistance." at **HTTP 200** (per OXA-000037), so monitoring shows a healthy route while these logins fail at 100%; the distinguishing cause ("invalid type: null, expected a string") exists only in server logs. Support cannot tell guest-null-mail failures apart from forged-state or IdP-outage failures — they are byte-identical to the user.
- **Severity P2, not P1:** no authentication bypass or data leak — no token is issued and the error path is otherwise sound (the `?`-propagation is exactly what makes this fail *closed*); the damage is complete functional exclusion of a user class plus misleading diagnosis. Not P3 because it is not cosmetic: it is total loss of login for affected identities, with no operator workaround short of hand-editing authority config (granting mailboxes) or DB rows.
- **Blast radius of the fix:** `MicrosoftProfile`, `retrieve_profile.rs`, and nothing else in the product path — the chain resolves *inside* the Microsoft strategy; downstream (`OAuth2Profile`, AOR, registrar, callback) never learns the difference. No wire/schema changes, so no migration.

## Proposed resolution

**Step 1 — make the wire shape honest (microsoft/mod.rs).**

```rust
pub struct MicrosoftProfile {
    pub display_name: Option<String>,
    pub given_name: Option<String>,
    pub surname: Option<String>,
    pub id: String,                    // Graph: Key, Not nullable — stays required
    pub mail: Option<String>,          // Graph: null for mailbox-less guests
    pub user_principal_name: Option<String>,  // camelCase rename → "userPrincipalName"
}
```

`user_principal_name` needs no `#[serde(rename)]` — `rename_all = "camelCase"` (`:30`) already maps it, which the file's own snake_case-rejection test (`:112-141`) proves for the name fields. Do **not** add blanket `#[serde(default)]`: keeping `id` required preserves the one signal that the body was really a Graph user.

**Step 2 — identifier fallback chain (decided: `mail → userPrincipalName → id`).** Add `MicrosoftProfile::identifier(&self) -> String` returning the first `Some` of those three, falling through to `id`. `retrieve_microsoft_profile` maps `email: profile.identifier()`.

Rationale for `mail`-first, decided against the `user_identifier` uniqueness analysis in §Analysis:
- **Continuity dominates.** Every existing row in `user_authorities` for this authority is keyed by the mail value; a `mail`-first chain resolves identically for all users who *have* mail — i.e. the chain is a strict superset of today's behavior and **zero existing users re-key**. A stability-first chain (`id` or UPN first) would re-key *every existing Microsoft user* (their rows say `mail`), logging everyone into a brand-new duplicate account — strictly worse.
- The residual re-key window is the single transition "guest registered under UPN fallback → tenant later provisions them a mailbox": next login derives `mail`, misses the lookup, and auto-registers a duplicate (`services/authenticate_or_register.rs:197-202`). This is accepted as documented residual risk — rare, one-time-per-user, fail-open (the human still gets in), and fixable by ops merging the two `user_authorities` rows. The conservative alternative (key everything by Graph `id`) requires an identifier migration plus a username/display split and is rejected here as a separate change; if anyone wants it, it belongs on top of OXA-000025's identifier-lookup work, not bolted into this fix.
- Uniqueness: `mail` is tenant-unique by Exchange construction, UPNs are directory-unique, Graph ids are global — a per-authority collision between one user's mail and another's UPN/id is vanishing, and the DB unique constraint is the backstop either way.
- Note in the code comment that the returned identifier may be a non-deliverable `#EXT#` UPN or an opaque id, and that it surfaces in `users.username` and the SPA `?email=` parameter (`callback.rs:106,132`) — deliberate, since those are display fields today.

**Step 3 — typed "no identifier" / malformed-profile error.** With `id` required, `identifier()` cannot return `None`; the remaining bad case is a body that fails to parse at all. Coordinate with OXA-000010 Step 3, which already reserves `OAuth2ProfileError` for `retrieve_*_profile.rs`: wrap the `.json()`/`try_into` failure as `OAuth2ProfileError::InvalidResponse { source }` (variant name per OXA-000010's landing; if this ticket lands first, keep the raw `?` and leave a `// TODO(OXA-000010)` — do not invent a competing enum). This is also the seam OXA-000037 Phase 3 downcasts for status classification; never leak the serde prose to the browser body (OXA-000037's anti-leak constraint).
