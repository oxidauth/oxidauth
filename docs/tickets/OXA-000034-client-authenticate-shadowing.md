# OXA-000034 — Inherent `Client::authenticate` shadows `AuthenticateTrait::authenticate`; one operation, two error types

## Problem

`authenticate` is the only method name in the SDK client that exists both as an inherent `Client` method and as a `ClientTrait` member method (inherent names: `new`, `test_client`, `get_jwt`, `get_jwt_decoded`, `authenticate`, `refresh`, `request`, `get`/`put`/`post`/`delete`; every other trait operation has a distinct name — e.g. inherent `refresh` vs trait `exchange_refresh_token`, and `register` is trait-only). Rust's method resolution always prefers inherent methods over trait methods, so:

1. **Every** `client.authenticate(u, p)` call site — inside the crate and for SDK consumers — resolves to the inherent version and gets `Result<bool, ClientError>`. The trait version is unreachable by method-call syntax on `Client` no matter whether `AuthenticateTrait` is in scope (and the prelude puts it in scope anyway), only via qualified syntax or generic/dyn dispatch over `ClientTrait`.
2. **The two entry points return different error types for one operation.** The inherent path yields the typed `ClientError` (`kind: ClientErrorKind`, inspectable by `match err.kind`); the trait path erases it into `BoxedError` (`oxidauth-kernel/src/error.rs:5`, `Box<dyn Error + Send + Sync + 'static>`) via `.into()`, so callers must `downcast_ref::<ClientError>()` to recover what the other entry point hands them for free.
3. **`Client` and `ClientMock` diverge at the same call syntax.** `client.authenticate(..)` → `ClientError`; `mock.authenticate(..)` → `BoxedError` (trait-only on the mock). Test code written against `Client` that matches `err.kind` cannot be reused against the mock; the generic route (`C: ClientTrait`) also gives `BoxedError`, so the mock-vs-production error contract is only consistent on the erased side.

Both paths execute identical logic — each is a one-line delegation to the same private `auth()` (POST `/auth/authenticate` + GET `/public_keys`, the wire contract pinned by the E1/E2 tests in `client/mod.rs` per the comment at `client/auth/authenticate.rs:43-47`). The split is purely API surface; the inherent wrapper adds zero behavior except skipping the trait impl's tracing span.

## Analysis

- **Mechanism.** Inherent impl > trait method is a language rule; there is no ambiguity error, no warning, and no way for a call site to notice it picked the "wrong" duplicate short of reading the error type. This makes the shadow silent by construction.
- **The pin is honest.** The `BUG(pinned)` comment at `client/auth/authenticate.rs:60-64` states the exact defect, and the test itself only proves the delegation + `ClientError → BoxedError` boxing survives (the `downcast_ref` at :69-71 works because `.into()` boxes the concrete `ClientError`, which implements `std::error::Error`, `client/mod.rs:641-647`).
- **Family convention.** Every other trait in the SDK (`RegisterTrait` — `client/auth/register.rs:12-17` — and the ~40 resource traits behind `ClientTrait`) returns `BoxedError`; the trait layer is the erased, dyn-friendly surface, while the inherent layer carries typed errors. `authenticate` accidentally exposes both layers under one name, which is why the register classifies it P3: no runtime misbehavior, but a permanent consumer-facing fork in one method's contract.
- **Reachability audit.** Within the repo the trait version is exercised only by the qualified-syntax test (`authenticate.rs:65`). The generic/dyn route is exported but unused (no `dyn ClientTrait` or `impl ClientTrait` consumers in the workspace), so any reachability risk of resolving the split lands almost entirely on downstream SDK users, not internal code.
- **Adjacent observation (not re-ticketed):** `ClientMock::authenticate_fn` (`client/mock.rs:228`) takes no arguments, so mock-backed tests can never assert on submitted credentials — unlike `register_fn`, which receives the request (`register.rs:52`). Whatever shape this ticket picks, the mock path remains the credentials-ignoring one.

## Impact

- **SDK consumers** are the affected party; the server never calls the SDK client. Concrete `Client` users get typed `ClientError` today and are unaffected until the split is resolved; anyone writing `C: impl ClientTrait` helpers, or testing with `OxidAuthClientMock`, gets `BoxedError` from the same-named call and must downcast to inspect `ClientErrorKind`. The trap is invisible in docs: the same method name documents one operation with two contracts.
- **Internal cost:** the crate's own 16 test call sites silently test only the inherent path; the trait path has exactly one test, reachable only through syntax no consumer would write. Any future change to `auth()` that forgot the trait impl would keep CI green except for that one pinned test.
- Tracing drift: the inherent call produces no `authenticate` span; the trait call does (`authenticate.rs:13`).

## Proposed resolution

**Recommended: unify the error type at `ClientError` and drop the inherent wrapper** — i.e. change `AuthenticateTrait::authenticate` to return `Result<bool, ClientError>`, delete `client/mod.rs:176-179`, and let one trait method be the only `authenticate`:

1. `client/auth/authenticate.rs`: trait signature (`:8`) and `impl AuthenticateTrait for Client` (`:12-19`) return `Result<bool, ClientError>`; the body becomes the bare `self.auth(username, password).await` (the `.map_err(|err| err.into())` disappears). Keep `#[tracing::instrument(skip(self))]`.
2. `impl AuthenticateTrait for ClientMock` (`authenticate.rs:26-34`) keeps its panic-on-unset behavior; the `authenticate_fn` field in `client/mock.rs:228` changes only its return type: `Option<Arc<dyn Fn() -> Result<bool, ClientError> + Send + Sync>>` (closure stays zero-argument).
3. Delete the inherent `authenticate` (`client/mod.rs:176-179`). Add `use crate::client::auth::AuthenticateTrait;` to the `client/mod.rs` test module (its `use super::*;` at :691 does not import it), or add `AuthenticateTrait` to the crate-internal re-export list at `client/mod.rs:22-38`.
4. Remove the now-false `BUG(pinned)` comment (`authenticate.rs:60-64`) and rewrite that test: `<Client as AuthenticateTrait>::authenticate(&client, …)` becomes plain `client.authenticate(…)`, and the `downcast_ref` assertions (:69-75) become direct `err.kind` matching. The test's meaning — "authenticate surfaces the underlying `ClientError`" — survives; its "re-types into BoxedError" clause is deleted with the conversion.

**Compat analysis (why this option):** it is the only proposal that is behavior-transparent at existing call sites. `client.authenticate(…)` sites that pattern-match `err.kind` (the 9 assertion sites in `client/mod.rs`) keep compiling with the *same* `ClientError` value *if* the trait is in scope — prelude users already have it (`prelude.rs:14`); non-prelude users get a loud "trait not in scope" error pointing at a one-line import, never a silent retyping. Generic/dyn `ClientTrait` code that previously wrote `-> Result<_, BoxedError>` fns with `client.authenticate(..)?` keeps compiling, because `Box<dyn Error + Send + Sync>: From<ClientError>` (std blanket impl) still converts on `?` — the same conversion the deleted `.into()` used. Breakage is confined to (a) the `mock`-feature field type at `client/mock.rs:228` (public under `feature = "mock"`; mock closures get shorter, not longer) and (b) any consumer who hand-implemented `AuthenticateTrait` expecting `BoxedError` — the trait's only impls in-tree are `Client` and `ClientMock`, and external impls of a client-for-APIs trait are implausible. The cost is convention: `AuthenticateTrait` becomes the one trait in the `ClientTrait` chain returning a typed error instead of `BoxedError` (see alternative B).

**Rejected alternatives:**

- **Rename the inherent method (e.g. `login`).** Keeps two implementations of one operation and the split error contract forever; worse, prelude users' `client.authenticate(…)` then silently binds the *trait* method and flips `ClientError → BoxedError` without any name change at the call site — the exact hazard this ticket exists to remove, smuggled into a rename. Also leaves `Client`/`ClientMock` asymmetric.
- **Drop the inherent, keep the trait returning `BoxedError`** (trait-only entry point, no error unification). One honest entry point with family-uniform `BoxedError`, and arguably the more "boring" long-term shape. But it re-types the error at every existing concrete call site that still compiles via the prelude, and forces the crate's 9 kind-matching assertion sites (`client/mod.rs:881, 914, 1132, 1150, 1165, 1176, 1204, 1213, 1243`) into `downcast_ref` boilerplate — more churn, and a worse typed-error story for the primary (concrete `Client`) user for zero functional gain over the recommended option.
- **Document the split, keep both entry points.** Rejected: nothing in the current split is load-bearing (the inherent wrapper has no behavior), so this only codifies a two-error-type API and keeps the mock asymmetry.

**Pin flips:** one — `client/auth/authenticate.rs:60-64` deleted, test rewritten per step 4 (assertions strengthen: plain-syntax reachability plus typed error, no downcast). The unrelated `BUG(pinned)` comments in `client/mod.rs` (966, 1074, 1290 — refresh/PEM/error-detail, covered by OXA-000028, OXA-000029, OXA-000030 respectively) must not be touched; note the PEM-pin test calls `client.authenticate` at :1243 and its error assertion needs the scope import from step 3, nothing more. Update `bin/test_client.rs:20`'s commented line if touched (it is commented; harmless either way). `docs/migration-plan/09-services-layer.md:274` refers to server usecase traits — not this API; leave alone. Related SDK tickets: OXA-000030 (CLI-4) argues for richer typed `ClientError` surfacing; this resolution moves `authenticate` toward that same typed surface; OXA-000027 (CLI-1) likewise operates inside the `client/mod.rs` wiremock suite.
