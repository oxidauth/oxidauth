## Problem

Three defects in one small module, all naming/contract rather than data-corruption class:

1. **Plural name, singular contract.** The module and every generated identifier (`SelectUserAuthoritiesBy…`) are plural, but the service returns exactly one `UserAuthority` via `fetch_one`. Inside this directory that is an active convention violation: plural `select_user_authorities_by_user_id` really returns `Vec`, singular `select_user_authority_by_user_id_and_authority_id` really returns one. A reader wiring a new use case cannot trust the name.
2. **Absent ⇒ `BoxedError` holding a `String`.** `RowNotFound` is rewritten at `mod.rs:32` into `format!("user authority not found: {:?}", err)` (displays as `user authority not found: RowNotFound`). `String` does not implement `Error` (the test comment `:102-103` notes Display-inspection is the only option), so no consumer can downcast or classify the miss. This is *by current design load-bearing*: AOR at `authenticate_or_register.rs:198-201` string-matches `"user authority not found:"` to decide "this OAuth2 email has never linked → register a new account". A typo in the postgres format string silently turns first-time OAuth2 logins into hard errors, and any DB outage inside `authenticate` *lacks* that substring — so the two outcomes are separated only by whether sqlx happens to stringify with those words elsewhere (it doesn't; outages propagate as `Err` → AOR returns `Err` → no registration, which is correct today only by accident of the match direction).
3. **The audit's "JSON-path lookup" premise never existed.** Nothing in the schema or any `.sql` file in `oxidauth-postgres` uses a JSON operator (`grep '->>|#>>|jsonb_|@>'` over `src/**/*.sql`: zero matches — no precedent anywhere in the repo). `user_identifier` is a first-class `VARCHAR(256)` column with its own index; the JSON→identifier mapping happens at the request boundary in the strategies (`username_password/user_identifier_from_request.rs:10-12` deserializes `AuthenticateParams { username, .. }`; `oauth2/user_identifier_from_request.rs:10-12` takes `email`). The audit mistook "identifier extracted from request JSON" for "lookup performed inside the `params` jsonb". The plural name (see 1) plausibly fed that misreading.

## Analysis

- **`fetch_one` can never hit `MoreThanOneRow`**: since migration `20240619063635`, `UNIQUE (user_identifier, authority_id)` bounds the `(authority_id, user_identifier)` predicate to ≤1 row; `insert_user_authority/mod.rs:127-158` pins the 23505 rejection and the same-identifier-different-authority allowance. So the *at-most-one* semantics are sound — the problem is purely the zero-row channel (String error vs `None`) and the name.
- **`{:?}` on `RowNotFound` is information-free** but benign: it renders `user authority not found: RowNotFound` — no identifier, no SQL leaked to the 400 response body (`IntoOxidAuthError` path at `oxidauth-api/.../authenticate.rs:42`). The live 400-not-404 not-found convention is already documented as probed in OXA-000021 ("Response …400 with `RowNotFound`/… debug strings"); this ticket must not silently change that status code.
- **Error-shape asymmetry with siblings**: `select_authority_by_client_key` claims `Option` and lies (OXA-000021, fix = `fetch_optional` + `transpose`, template at `select_authority_by_strategy/mod.rs:18-23`); here `Response` honestly says `UserAuthority` and the miss is an error — a defensible design, since the only caller that *needs* negative semantics is AOR, and both `authenticate` and `update_password` genuinely want "present or fail". The `None`-vs-error choice is thus a design decision, not a bug per se; the *bug* is that the decision is encoded as an untypeable `String` and consumed by substring match.
- **Adjacent risk (out of scope, note only)**: identifier equality is case-sensitive VARCHAR. Because AOR auto-registers on not-found, `Alice@x.com` vs `alice@x.com` from an OAuth2 provider creates a second user rather than a failed login. Normalization belongs to the strategies/`register`, not to this query; record under whichever item owns identifier normalization (same family as DATA-13's "unspecified semantics" notes — not re-ticketed here).
- **`update_password` error swallowing** (`:107-109`) is the same `let Ok(_) else` anti-pattern the OXA-000009/OXA-000015 family catalogs: during a DB outage, users are told "Failed to find user by username". Fixable in passing by the caller-side half of this ticket.

## Impact

- **Maintainers / future callers** (primary): the plural name invites treating the service as a list query (as the audit itself did); the tracing span actively misdirects log greps to a nonexistent `by_user_id` lookup.
- **OAuth2 link-on-first-login (AOR)**: correctness depends on an exact substring crossing a crate boundary (`oxidauth-postgres` format string → `oxidauth-services` matcher). No compiler or test-adjacent signal protects the contract except mock re-formatting (which re-formats *the same string*, `authenticate_or_register.rs:565-571`, so the mocks cannot catch a divergence — they assume what they check).
- **Login UX/API**: unknown username at login is a 400 carrying `user authority not found: RowNotFound` — fine under the repo's probed convention; a DB outage is *also* a 400 with a different string (no 5xx anywhere), which masks outages in monitoring.
- No data-integrity, auth-bypass, or wrong-row exposure: the predicate is correct and unique-bounded. P3 holds.

## Proposed resolution

**Rename now; typed error next; JSON-path question closed as "not intended".**

1. **Rename to singular** — `select_user_authorities_by_authority_id_and_user_identifier` → `select_user_authority_by_authority_id_and_user_identifier` (module dir, `.sql` filename, `include_str!`, repository file, trait `SelectUserAuthorityByAuthorityIdAndUserIdentifierQuery`, params struct; no collision with the existing `select_user_authority_by_user_id_and_authority_id` — distinct keys, distinct names). Touch points: postgres module + its `mod.rs:3` declaration, repository `user_authorities/mod.rs` re-export, and the three service files + their mocks listed above. No kernel changes (params live in oxidauth-repository); `oxidauth-api/src/provider/services.rs` satisfies traits via blanket impls and does not name the trait (grepped). Pre-1.0 workspace, no external consumers — no deprecation shim.
2. **Fix the tracing span** at postgres `mod.rs:16` to `select_user_authority_by_authority_id_and_user_identifier_query` in the same rename commit.
3. **Type the not-found channel** (follows OXA-000021's error-taxonomy direction and OXA-000010's "replace `format!` errors with typed errors"): add `UserAuthorityNotFoundError { authority_id, user_identifier }` in `oxidauth-kernel/src/user_authorities/` (pattern: `AuthorityNotFoundError`, `kernel/src/authorities/mod.rs:159-191`), return it from `mod.rs:32` instead of the `format!`. Keep `Response = UserAuthority` and `fetch_one` — do **not** switch to `Option`/`fetch_optional`: the honest `UserAuthority` + typed NotFound is what both consumer shapes need (authenticate/update_password fail, AOR branches), and it preserves today's 400-status wire behavior. AOR then matches `err.downcast_ref::<UserAuthorityNotFoundError>()` (`:198-201`) instead of `contains("user authority not found:")`; `update_password.rs:107-109` downcasts NotFound → its "Failed to find user by username" 400 and propagates real errors as `?` (fixes the outage-swallow in passing). Compat: the Display string of the typed error keeps the prefix `user authority not found:` so any out-of-repo consumer grepping it is unaffected during transition.
4. **JSON-path question: document, don't build.** Add a comment above the SQL (or in `user_authorities/mod.rs`) stating that login-identifier lookup is deliberately a first-class-column equality — identifier extraction from request JSON is owned by `UserIdentifierFromRequest` strategies; a future "identifier = arbitrary userinfo field" requirement belongs there, not in a SQL `params ->>` predicate. Reject the audit's implied feature ask.

**Pinned-test flips** (grep `BUG(pinned)` in `oxidauth-postgres/src/user_authorities/`: exactly this one, `mod.rs:58-62` — remove the marker on resolution; its text is accurate so it becomes a resolved-by-design comment or disappears):

- postgres `it_should_map_absent_identifier_to_a_not_found_error` (`:88-123`): assertions `starts_with("user authority not found")` still pass under the Display-preserving typed error; strengthen to also `downcast_ref::<UserAuthorityNotFoundError>()` on the typed error (the whole point of the fix) and keep the cross-authority scoping case `:110-122`.
- services `authenticate.rs` mock NotFound arm `:458-459` → return the typed error; assertion `:960` ("user authority not found") keeps passing via Display; optionally assert the type.
- services `authenticate_or_register.rs` mock `:565-571` → typed error; its registration tests now exercise the *real* branch condition (downcast) instead of a shared-substring tautology.
- services `update_password.rs` mock `:290-301` → typed error for its NotFound outcome.
