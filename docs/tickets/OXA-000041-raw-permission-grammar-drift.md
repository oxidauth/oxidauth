## Problem
Two independent parsers enforce two different grammars for the same `realm:resource:action` string:

1. **Kernel `RawPermission::try_from(&str)`** (`oxidauth-kernel/src/permissions/mod.rs:56-84`): `value.split(':')`; rejects `parts.len() < 3` (`:62-67`) or an empty segment among the first three (`:69-76`); then keeps `parts[0..3]` and **discards everything after the third colon** (`:78-82`). It also imposes no character restrictions — any non-empty bytes are legal segments.
2. **oxidauth-permission `parse()`** (`oxidauth-permission/src/tokens/parse.rs:3-101`): a token-level grammar — dynamic parts only `[a-zA-Z0-9_-]` (plus `.` sub-parts), `*`/`**` wildcards, and a colon counter that returns `InvalidPermission` on the **third colon**, i.e. any 4+ segment string (`:36-40`). `parse_fail` additionally rejects whitespace, `***`, leading/empty segments (`:188-205`).

So `RawPermission::try_from("a:b:c:d")` succeeds as `{realm:"a", resource:"b", action:"c"}` — pinned at `oxidauth-kernel/src/permissions/mod.rs:164-174` — while `oxidauth_permission::parse("a:b:c:d")` is pinned to *error* at `oxidauth-permission/src/tokens/parse.rs:194`. Same crate family, two grammars, both assertions "correct" by pin.

**Register line drift confirmed:** the cited `:165` is the `BUG(pinned)` comment in the kernel test module, not the defect; the defect is the `TryFrom<&str>` body at `:56-84`.

## Analysis
The **write path** (postgres insert / select-by-parts / delete-by-parts) speaks grammar 1. The **authorization path** speaks grammar 2: every guarded handler validates the caller's entitlement strings via `parse_and_validate`, and `/can` parses challenges via `parse` and grants via `validate`. Entitlement strings are rebuilt from DB rows by `Permission::Display` (`oxidauth-kernel/src/permissions/mod.rs:22-26`, plain `{realm}:{resource}:{action}`), so whatever the write path stored is re-serialized verbatim into grammar-2 validation at check time.

What happens to `"a:b:c:d"` today, end to end:

- `POST /v1/permissions/a:b:c:d` → services pass it through verbatim → `insert_permission/mod.rs:17` parses it to `a:b:c` → a row `{a, b, c}` is inserted and returned as success (`create_permission.rs:44-52`). The API stored a permission the client never asked for, with no error and no warning; the response `Display` reads `a:b:c`.
- Truncation silently aliases all three CRUD ops on the same key space:
  - create `a:b:c` then create `a:b:c:d` → the second fails on `unique_grant_parts` with a duplicate error about a string the caller never typed;
  - `DELETE /v1/permissions/a:b:c:d` (`delete_permission/mod.rs:16-24`) **destructively deletes row `a:b:c`**;
  - `GET /v1/permissions/a:b:c:d` (`select_permission_by_parts/mod.rs:20-27`) returns row `a:b:c` as if found.
- The truncated row is itself grammar-2-parseable (3 segments), so no error at match time — but the intended name is unchallengeable: `/can/a:b:c:d` → `parse` error → HTTP 400 `"invalid permission"` (`can/mod.rs:22-24`). Create-time accepts what check-time rejects.
- **The gap is wider than segment count.** Because grammar 1 only requires non-empty segments, any storable-but-grammar-2-invalid row poisons matching: e.g. `"my realm:users:read"` (whitespace), `a:b:rea$d`, unicode segments — all storable via the same POST, all rebuilt verbatim by `Display`. And `validate()` **short-circuits on the first `Err` over the whole grant list** (`oxidauth-permission/src/tokens/mod.rs:57-70`: any parse failure returns `Err` before the remaining grants are examined), so one such row granted to a user turns *every* grammar-2 check for that principal into an error — a 400 in the per-handler guard (e.g. `create_permission.rs:26,33`) and `CanError::BadPermissions` in the middleware surface (`oxidauth-api/src/middleware/can.rs:66`) — even when the user also holds a valid matching grant. Grammar 1 is the only writer gate, so a typo at create time becomes a persistent availability failure for that principal's authorization checks.
- **No such data exists today.** The only 4+ segment string literal in the tree is the test fixture `"a:b:c:d"` (`oxidauth-kernel/src/permissions/mod.rs:166,168`; `oxidauth-permission/src/tokens/parse.rs:194`; plus an unrelated password-hash fixture at `oxidauth-services/src/auth/strategies/username_password/helpers.rs:49`). Bootstrap constants are grammar-clean (`oxidauth-services/src/bootstrap/mod.rs:248-249`: `oxidauth:**:**`, `oxidauth:totp_code:validate`, used by `first_or_create_permissions`, `:252+`); hurl/seedz fixtures contain only 3-part grammar-valid strings (`demo:dashboard:view`, `demo:reports:export`, `oxidauth:**:**`, `oxidauth:totp_code:validate`). Note `seedz/src/fixtures.rs:262-267` inserts the three columns *directly*, bypassing both parsers — that bypass is how `*`-literal rows are testable (`select_permission_by_parts/mod.rs:80-81` comment: "kernel RawPermission accepts any non-empty parts, so '*' rows are storable") and is a second writer that any migration audit must cover.
- `oxidauth-rs`, `oxidauth-cli`, and `oxidauth-import-export` never parse permission strings themselves (no `RawPermission` / grammar-parser hits); they forward user input and inherit whatever the server accepts.

## Impact
Who: anyone calling `POST/GET/DELETE /v1/permissions/{permission}` (admin tooling, `oxidauth-rs` callers, hurl scripts), and every deployment whose `permissions` table may contain grammar-1-only rows (including via seed tooling that bypasses both parsers).

- **Silent data-integrity drift** — requested name ≠ stored name, with a success response; audit trails and UI show the truncated name.
- **Destructive aliasing** — `DELETE .../a:b:c:d` removes row `a:b:c`; `GET .../a:b:c:d` fabricates a hit on it.
- **Cross-parser inconsistency** — a name accepted at create time is rejected at `/can` time (400); duplicate-key errors reference strings the caller never sent.
- **Per-principal authorization-check DoS** (the non-count half of the same gap): one storable-but-unparseable granted row makes every grammar-2 check for that holder return 400/`BadPermissions`, because `validate` short-circuits `Err` over the whole grant list.
- Not privilege escalation: no path lets a 4-part string match something it shouldn't — the damage is integrity plus availability of authorization checks, not bypass. P2 fits the register.

## Proposed resolution
Make oxidauth-permission's `parse()` the single source of truth; the kernel already depends on the crate (`oxidauth-kernel/Cargo.toml:14`), so this is an in-crate delegation, not a new dependency.

1. **Kernel delegates validation.** In `RawPermission::try_from(&str)` (`oxidauth-kernel/src/permissions/mod.rs:56-84`), call `oxidauth_permission::parse::parse(value)` and require the accepted shape before splitting: exactly three `:` segments, each non-empty, each matching the crate's character class (dynamic `[A-Za-z0-9_-]` or `*`/`**`). Keep the `RawPermission` struct, its three fields, and all four `TryFrom` impls (they already funnel through `&str`). Decision point to record in the PR: the crate also accepts dotted hierarchies (`oxidauth.admin_web…:tenant…:read…`, pinned at `parse.rs:156-185`) while `RawPermission` would flatten a dotted realm into one column — either gate kernel strings to the plain 3-part form (recommended: matches the SQL schema's three columns and the `=`-equality lookups) and note the crate's dotted acceptance as crate-only forward grammar, or adopt it fully; do not leave it ambiguous.
2. **Error-message impact.** Today: `"a permission must have all three parts: '{value}'"` (`mod.rs:63-66,70-74`), surfaced verbatim as `BoxedError` → `Response::bad_request().error(err.into_error())` (`oxidauth-api/src/server/api/v1/permissions/create_permission.rs:59`, `delete_permission.rs:59`). `PermissionParseErr::InvalidPermission` displays only `"invalid permission"` (`tokens/mod.rs:24-31`), dropping the input echo. Preserve the echo kernel-side, e.g. `format!("invalid permission '{value}': expected realm:resource:action, three non-empty parts of [A-Za-z0-9_*-]")`. Postgres tests assert `contains("all three parts")` at `insert_permission/mod.rs:118,130` and `select_permission_by_parts/mod.rs:112` — either keep that substring in the new message for the `< 3` case or update all three assertions deliberately.
3. **Audit + migration for stored rows.** Ship the validation change together with a read-only audit query (no auto-rename of grants — renames silently rewrite who-can-do-what):
   `SELECT id, realm, resource, action FROM permissions WHERE realm !~ '^[A-Za-z0-9_-]+$' AND realm NOT IN ('*','**') OR resource … OR action …;` (same predicate per column; plus an application-side `Display` re-parse check to catch embedded colons). Repo-shipped data is clean (see Analysis), so this is a no-op on fresh installs; real deployments quarantine (ungrant) offending rows manually. The `oxidauth-import-export` and `seedz` column-direct writers (`seedz/src/fixtures.rs:262`) should route through the same validation or be listed as trusted-internal.
5. **Pinned-test flips** (related `BUG(pinned)` markers grep-matched: only `oxidauth-kernel/src/permissions/mod.rs:165` is grammar-related; `auth/tree/mod.rs:291`, `postgres/auth/tree/mod.rs:380`, `postgres/permissions/update_permission/mod.rs:36` → OXA-000014 — scheduled as REMOVAL 2026-09-30, that file and its marker get deleted, never flipped —, `bootstrap/mod.rs:1641` are unrelated):
   - `oxidauth-kernel/src/permissions/mod.rs:163-174` `raw_permission_silently_drops_parts_beyond_the_third` — flip `try_from("a:b:c:d").unwrap()` / `action == "c"` to `unwrap_err()`; rename to e.g. `raw_permission_rejects_four_part_strings`; delete the `BUG(pinned)` comment at `:165-167`.
   - `oxidauth-postgres/src/permissions/insert_permission/mod.rs:106-139` `it_should_reject_malformed_permission_strings_before_touching_the_db` — keep; add an `"a:b:c:d"` (and a `"my realm:users:read"`) case asserting pre-DB rejection and `COUNT(*) = 0`; align `:118,:130` substring with step 2.
   - `oxidauth-postgres/src/permissions/select_permission_by_parts/mod.rs:101-115` — same message coupling at `:112`.
   - Must stay green: `oxidauth-permission/src/tokens/parse.rs:188-205` `parse_fail` (already the target grammar); kernel `:122-136` `raw_permission_parses_valid_three_part_strings` (incl. `"oxidauth:**:**"` — `**` is grammar-2-legal); `:138-161` empty/short-segment cases (message coupling only); `oxidauth-postgres select_permission_by_parts:78-99` wildcard-literal test (`oxidauth:*:read` stays storable — `*` is legal in both grammars); `oxidauth-services create_permission.rs:96-110` (delegate purity unaffected).
5. **Compat.** No wire-format change for valid strings; requests that previously 2xx'd via silent truncation now 400. That is the changelog line: stricter input validation on `/v1/permissions/{permission}` — behavior fix, not API change. Changelog notes go per repo convention (`changelogs/`).
