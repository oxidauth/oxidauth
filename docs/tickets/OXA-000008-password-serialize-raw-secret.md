## Problem

`Password` is a redaction *type by convention*: `Debug` is hand-masked, raw access is `inner_value()` (`lib.rs:82-84`), and it is deliberately deserializable from JSON bodies — but the derived `Serialize` means `to_json(password) == the secret`, with no compile-time or runtime signal. Any code that ever puts a `Password`-bearing DTO into a response body, a webhook payload, a `tracing` event recorded with `serde_json`, an error envelope, or an export artifact ships the raw credential. The type protects the `{:?}` path (and thus all `tracing::instrument`-recorded arguments) while leaving the `serde` path wide open — and unlike `JsonValue`, where raw serialization is the point of the type, for a password it is only ever needed at the instant of hashing.

The register's counter-warning is a real hazard but is misfiled: what actually depends on raw-serialization passthrough is `UpdatePasswordParams` (String fields), and the pin test's own comment (`lib.rs:133-135`) inherits that misattribution.

## Analysis

**Mechanism.** `#[derive(Serialize)]` on a one-field tuple struct delegates to `String`'s impl — the secret appears on the wire under whatever key the DTO field carries. Redaction was consciously designed for `Debug` only (`lib.rs:89-92` comment); `Serialize` was derived "for symmetry" with `Deserialize`.

**Full enumeration of `Password::serialize` callers (grep-verified over the whole workspace):**

| Site | Direction | Consequence if `Serialize` removed/redacted |
|---|---|---|
| `bootstrap/mod.rs:462-471` via `registrar.rs:93-97` `to_value()` | in-process handoff into `RegisterService` | **Removal:** compile error (loud, in the one place that must be touched). **Redaction:** *silent corruption* — see edge case below. |
| `UsernamePasswordAuthenticateInputs` / `UsernamePasswordRegisterInputs` derives (`authorities/…/authenticate.rs:41`, `register.rs:53`) | none — never serialized anywhere, strategy is test-only | Compile-time dead code; safe to drop. |
| everything else (webhook `WebhookReq` `kernel auth/authenticate.rs:59-64`, oauth2 exchange reqs, client bodies, response DTOs, import/export) | — | no `Password` field involved; unaffected. |

**The redact-instead-of-remove trap (why the register's fear is legitimate even though its target is wrong).** If `Serialize` were changed to emit the constant mask, `bootstrap:462-471` would keep compiling and produce `{"password":"******", …}`; `Password`'s `Deserialize` accepts any string (`lib.rs:74`, no validation — `Password::new`/`From<String>` at `:77-84`, `:96-99` accept anything), so the registrar would happily hash and store `******` as the admin's password while `bootstrap:460` prints a *different* (env-set or random) password to stdout — a silently dead admin account and a mismatched credential on every cold start with no TTY-visible error. CI would catch it only via the bootstrap test fakes (`mod.rs:1104-1108` + assertions at `:1453-1458`, `:1490-1497`). A *removal* makes this a compile error at the one site that must be redesigned — the loud failure the redacted-serialize variant hides.

**The active leak is real, but it is `Debug`-on-String, not `Password`.** On the forgot/recovery-password path, `UpdatePasswordParams { code, username, client_key, password, password_conf }` (kernel `update_password.rs:10-17`) derives plain `Debug`, and all three `#[tracing::instrument(.., skip(self))]` layers (api handler, service use case, SDK wrapper) record the `params` argument through `Debug` by default. Any subscriber that records span fields (e.g. `json` format) persists the user's **new password, its confirmation, and the 2FA recovery code** in plaintext logs. `Password` is exactly the tool that would prevent this — but it is not used at that boundary *and cannot be used naively there*: the SDK serializes the same struct to the request body (`client/mod.rs:472-473`), so a masked `Password::Serialize` would send `******` as the new password while a removed `Serialize` would break the wrapper's compilation. That asymmetry (inbound server-side `Debug` needs redaction; outbound wire needs raw) is the reason this ticket proposes masking `UpdatePasswordParams::Debug` explicitly instead of retyping its fields.
Note the same DTO's `code` is the SEC-5 TOTP recovery code — its log exposure is a second consumer of the fix.

**Boundary honesty.** Redacting `Password::Serialize` does not make the server "password-free": request bodies arrive as `JsonValue`, which serializes raw by design (`lib.rs:36-37`), and any code holding `inner_value()` can still write the secret. The fix narrows the *accidental* surface (typed DTOs can no longer serialize secrets at all) so that carrying raw material requires an explicit `String` and an explicit decision.

**Who is affected today.** No wire or stored artifact carries a `Password`-serialized secret today (audited above) — the exposure is (a) the live tracing-span leak on every `update_password` call through the server or the SDK, and (b) any future response DTO, webhook, telemetry, or export that embeds a `Password` field will silently exfiltrate it unless the reviewer happens to notice; the type currently *encourages* embedding it (it is deserializable, cloneable, and — misleadingly — serializable).

## Impact

- **Confidentiality (active):** new-password plaintext (and the recovery code) in server logs and in any SDK-app logs wherever tracing span fields are recorded — for every password-reset completion, until SEC-5's redesign removes the flow. Log readers, log pipelines, crash-report collectors, and anyone with log-bucket access hold users' fresh passwords.
- **Confidentiality (latent):** every `Password`-typed field is one `#[derive(Serialize)]`-adjacent mistake away from shipping credentials in API responses or webhooks; nothing in the compiler, clippy, or tests stops it.
- **Correctness trap:** the obvious one-line "fix" (mask `Serialize`) silently corrupts bootstrap admin provisioning — see Analysis — which is precisely the failure mode the register's "do not fix without auditing" warns about.
- Severity P2 is right: an active but log-scoped secret exposure plus a latent footgun; no remote credential disclosure today.

## Proposed resolution

**Step 1 — remove `Serialize` from `Password`; keep `Deserialize` (loud, not silent).**

1. `oxidauth-kernel/src/lib.rs:74`: `#[derive(Clone, Deserialize)]`. Drop the `BUG(pinned)` comment and rewrite the test (below). `Deserialize` must stay — every inbound parse goes through it (`authenticator.rs:25-33`, `registrar.rs:99-107`, axum `Json<..>` handlers). Add a doc comment on the type: *raw material is reachable only via `inner_value()`; this type deliberately does not implement `Serialize` — build `json!({...})` from an explicit `String` when a wire payload genuinely needs the raw value (precedent: `oxidauth-rs/src/client/mod.rs:235-238`).*
2. `registrar.rs:82`: `#[derive(Clone, Deserialize)]`; delete `to_value()` (`:93-97`) — its only caller is bootstrap.
3. `bootstrap/mod.rs:462-476`: build the handoff JSON explicitly from the raw `String` (`json!({"username": …, "password": password, "password_confirmation": password, "kind": "api"})`, mirroring `client/mod.rs:235-238`); no `Password` instances needed there since the payload is only re-parsed by the registrar. The register-side wire contract and the fake's payload assertions stay identical.
4. `authorities/…/authenticate.rs:41` and `register.rs:53`: drop `Serialize` from both input structs (keep `Debug` — the masking pin at `register.rs:63-73` stays green). These strategies are test-only, so this is free.
5. Rejected alternative (record the decision): `impl Serialize` emitting `"******"`. It preserves compilation everywhere *except* the one place that must be redesigned, and turns `bootstrap` into silent `******`-password corruption that parses cleanly on the receiving side (Analysis). If a masked-serializable secret type is ever genuinely wanted, make a separate `Redacted<T>` newtype rather than repurposing `Password`.

**Step 2 — plug the live log leak in `UpdatePasswordParams`.** Replace `#[derive(Debug)]` at `oxidauth-kernel/src/auth/username_password/update_password.rs:10` with a hand-written `Debug` that constant-masks `password`, `password_conf`, and `code` (same shape as `Password`'s `lib.rs:87-94`: no length, no prefix). One change covers all three instrument layers (`api …/update_password.rs:12`, `services …/update_password.rs:76`, `oxidauth-rs …/update_password.rs:12`) because they all record the same type. Do **not** retype the fields to `Password`: the SDK serializes this struct to the request body, so either masked or missing `Serialize` breaks the wire contract; keep `#[derive(Serialize, Deserialize)]` and the raw String fields, and let the custom `Debug` be the redaction. (Longer term, SEC-5's single-use-code redesign will replace this DTO; a masked `Debug` is a one-file stopgap that no consumer can observe on the wire.)

**Compat/migration.** No wire, DB, or API change anywhere: verified nothing persisted (`user_authorities.params` stores only `{password_hash}` — `registrar.rs:53-61`, `user_authority_from_request.rs:34-46`, `services …/update_password.rs:143-151`) or transmitted contains a serialized `Password`. Removing a trait impl is a breaking change for external `oxidauth-kernel` (0.9.0) consumers who serialize the type — none exist in-workspace; call it out in the changelog alongside the 0.9.0 `oxidauth-http::response` deprecation precedent. No migration; the hurl suite passes passwords as raw body strings from env vars (`src/oxidauth/hurl/tests/authenticate.hurl:10-11` etc.) and never touches the kernel type. If Step 1 lands without Step 2, keep a follow-up note — SEC-5's redesign must not resurrect a debug-derivable password field.

**Pinned-test handling (grep-verified).** Exactly one `BUG(pinned)` marker relates to this item (workspace-wide grep for markers mentioning password/serialize/secret):

- `oxidauth-kernel/src/lib.rs:133-135`, inside `password_serde_carries_the_raw_value` (`:131-145`) — **flip**: delete the marker comment and the `to_value` assertion (`:138`); keep the `from_value` leg (`:139-144`, `Deserialize` still works); add a compile-time red pin that `Password: !Serialize`, e.g. `fn _assert_not_serializable<T: Sized>() where T: serde::Serialize {}` never monomorphized on `Password`, or the standard negative-bound trick / a doc test showing the type has no `Serialize` — plus keep `password_debug_redacts_the_secret` (`:110-121`) untouched.
- `oxidauth-services/src/bootstrap/mod.rs:1453-1458` and `:1490-1497` (register payload carries the raw admin password) — **no marker, but the functional pin the register meant.** They must stay **green** after Step 1: bootstrap's explicit `json!` build keeps the payload raw, which is the whole point of the design.
- `oxidauth-services/src/authorities/strategies/username_password/register.rs:63-73` `testing_manual_password_debug_impl` (Debug masks the embedded `Password`) — **keep**; verify it still passes after the `Serialize` derives are dropped.
- `oxidauth-rs/src/client/mod.rs:817-837` (E1 authenticate body) and `oxidauth-rs/src/client/auth/username_password/update_password.rs:37-58` (update_password wire contract) — **keep green**; Step 2 is `Debug`-only and must not alter these bodies.
- Unrelated markers reviewed and excluded: `helpers.rs:45-48` (SEC-7 colon joiner), `forgot_password` client turbofish pin (SEC-5 item), `oauth2/callback.rs:322`.
