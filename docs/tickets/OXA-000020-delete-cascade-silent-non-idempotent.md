## Problem

Two distinct behaviors the 2022 audit (A1/A2) flagged, both confirmed against current code:

1. **Silent cascade destruction.** `DELETE /v1/users/{id}` with `oxidauth:users:manage` irreversibly destroys, in one statement, every grant (`user_role_grants`, `user_permission_grants`), every identity link (`user_authorities`), every session (`refresh_tokens`), and every 2FA enrollment (`totp_secrets`) of that user; `DELETE /v1/authorities/{id}` destroys every `user_authorities` link and every `refresh_tokens` row issued under that authority. The audit expected Postgres to *reject* deletes with dependents; the schema instead guarantees the delete always succeeds and nobody is told what collateral died — there is no audit log, no count in the response (`Response` is just the deleted row), and no admin preview.
2. **Non-idempotent delete.** Because `Response = User`/`Authority` is non-optional and the query is `DELETE … RETURNING *` with `fetch_one`, deleting an already-absent id returns `Err(RowNotFound)` → HTTP 400 `"database row not found"` — indistinguishable on the wire from a malformed request. Retries after a timeout, terraform/automation reconcile loops, and double-clicked admin panels all observe "failure" against a state that is already the desired end state.

## Analysis

**The audit expectation is half wrong; the register's complaint is half right.** Blanket FK rejection (the A1/A2 expectation) would be *worse* semantics: grant rows, refresh tokens, and TOTP secrets have no meaning independent of their user — RESTRICT would turn every user delete into a manual multi-endpoint sweep and would not actually save any data (orphaned grants to a dead user are garbage, not audit). The genuinely objectionable property is that the destruction is *unobservable*, not that it happens. The one place the current schema gets the policy backwards is `invitations` — the sole dependent that is itself a live bearer capability — and it fails in the opposite direction (no FK, dangling rows); OXA-000013 already proposes a `RESTRICT`-style FK for exactly that table, and this ticket must not re-litigate it. The two proposals are complementary: OXA-000013 blocks deletes of invite-placeholder users while an offer is pending; this ticket makes the remaining cascade visible and makes repeat deletes well-behaved.

**Permission-boundary erosion (verified consequence):** deleting a user under `oxidauth:users:manage` destroys `user_authorities` credential links — data otherwise reachable only via `oxidauth:authorities:manage` flows — with a single call and no record. Deleting a user also silently *un-2FA's the identity*: recreating a same-username account (username is the login key; `user_authorities` identifier uniqueness is per `user_id`, migration `20240619063635`) yields a password-only account because `totp_secrets` cascaded. `refresh_tokens` cascade is the one side effect everyone actually wants (a deleted user's sessions must die) — yet even that count is invisible; the adjacent pin at `oxidauth-postgres/src/refresh_tokens/delete_refresh_token_by_user_id/mod.rs:58-60` shows the same "cannot count what was revoked" defect in the explicit logout path, so no current endpoint can report a revocation count either.

**Why idempotency is not a one-line fix — the contract chain:** the "return the deleted row" API is load-bearing down the whole stack. Repository traits (`Response = User`/`Authority`) force `RETURNING *` + `fetch_one`; handlers wrap whatever comes back into `payload.user` / `payload.authority`; hurl asserts `$.payload.user.id` (`users.hurl:138-140`); the oxidauth-rs typed wrappers *require* a non-empty payload and error `EmptyPayload(User, "delete_user")` on `success: true` with no payload (contract leg 3, `client/users/contract.rs:171-193`). A "true no-op" delete (second call → `Ok`/`204`/payloadless `200`) therefore breaks the client wrapper and the hurl assertion unless the DTO, wire shape, client trait, and contract tests all move together. A 404-style fix (second call → typed not-found error → HTTP 404, payload contract intact on success) needs no wire change on the success path and the client still surfaces it as an error (`APIResponseError`, leg 2) — idempotency in the "converged, distinguishable, retry-safe" REST sense rather than the "silently succeed" sense.

**Cascade coverage is already inconsistent**, which strengthens the "documented cascade" option over the RESTRICT option: the delete that *most* needs to fail (pending invitations) doesn't cascade today *because of a different bug* (OXA-000013's missing FK), while every FK that exists cascades. Whatever policy is chosen must be applied uniformly across users, authorities, roles, and permissions deletes — `DELETE /v1/roles/{id}` silently strips grants from every user holding it via `user_role_grants`/`role_role_grants`, and `roles/delete_role/mod.rs:55-67` already pins the same non-idempotence as an accepted behavior.

**Soft delete (a `UserStatus::Deleted` tombstone) was considered and is out of scope here:** every read path (`select_all_users_query`, `select_user_by_*`, auth tree, invitations consumer, OXA-000009's status-transition surface) would need status filtering simultaneously — a larger, riskier change that deserves its own design ticket if product wants restorability rather than auditability.

## Impact

- **Who:** every self-hosted deployment using the shipped, permissioned `DELETE` endpoints; the oxidauth-rs client for anyone automating against them; ops/automation that retries deletes.
- **Data/audit:** no forensic record of what a user delete destroyed (grants = authorization history; `user_authorities` = which external identities mapped to whom). Post-hoc compliance questions ("who could this user act as, at deletion time?") have no answer in the database.
- **Security:** deleted-then-recreated usernames silently lose 2FA and all prior linkage; an admin can destroy another team's authority links with only `users:manage`. Not privilege *escalation* — it is untracked privilege *destruction*.
- **UX/automation:** the double-delete 400 `"database row not found"` teaches integrators that the API "failed"; scripts learn to pre-check existence (a TOCTOU-prone extra round-trip) or suppress errors wholesale, masking real failures.
- **Severity:** P2 — no auth bypass, but irreversible, unobservable data destruction plus a wrong-status-code contract defect on a live endpoint pair.

## Proposed resolution

**Recommended shape: keep CASCADE, make it loud; make repeat deletes deterministic 404s; leave `invitations` to OXA-000013.**

1. **Cascade audit log (both repos).** Wrap each delete in one explicit transaction on the write pool (`self.db.write_pool().begin()`): run per-table `SELECT COUNT(*) … WHERE user_id = $1` (grants, authorities-links, refresh tokens, TOTP for users; `user_authorities` + `refresh_tokens` for authorities), execute the `DELETE … RETURNING *`, commit, then `tracing::warn!(target: "audit", user_id, cascade_totp = n, cascade_tokens = m, …)`. The counts ride indexes that already exist (`user_authorities_user_id_idx`, `refresh_tokens_user_id`, `totp_secrets_user_id`, …). This preserves atomicity (same transaction) and requires no schema change. Persisting an `audit_log` table can be a follow-on; the log line closes the "silent" half of the defect.
2. **Idempotent-by-status (404, not 200):** add kernel unit errors (e.g. `oxidauth_kernel::users::delete_user_by_id::UserNotFound`, mirroring the `oxidauth:users:manage` boundary; same for authorities) implementing `std::error::Error`. In both `mod.rs` executors swap `fetch_one` → `fetch_optional` and return `Err(BoxedError::from(UserNotFound))` when no row was deleted (count-0 path from step 1 tells us it was already absent). Add `Response::not_found()` (`StatusCode::NOT_FOUND`) to `src/xlib/http` (it has no helper today). In both handlers `downcast_ref::<UserNotFound>()` in the `Err` arm → `Response::not_found()`, everything else stays 400. Success-path wire shape is untouched, so hurl leg 1 and the client contract (legs 1–3) keep passing; the second delete becomes a documented, retry-safe 404 ("already deleted"), distinguishable from request garbage.
3. **Pin flips (exact):**
   - `oxidauth-postgres/src/users/delete_user_by_id_query/mod.rs:85-94` — keep the "second delete errors" assertion but re-pin the error to `UserNotFound` (still `Err`, so the assert-shape change is `contains("RowNotFound")` → the typed name); if product instead demands a `Ok` no-op, this whole block inverts and step 2 must be widened down the DTO/client chain (§Analysis), flipping `client/users/contract.rs` legs 2–3 and `users.hurl:134-141` too.
   - `oxidauth-postgres/src/authorities/delete_authority/mod.rs:105-114` — same flip; also add the missing `BUG(pinned)` marker when rewriting, since it is currently an unmarked pin.
   - CASCADE pins `users/…/mod.rs:68-83` and `authorities/…/mod.rs:86-103` — do **not** invert: option keeps CASCADE; rewrite the comments to "intended: dependent capabilities die with the owner; visibility via audit log (this ticket), invitations covered by OXA-000013" and downgrade them to intent assertions. The services-level intent comments (`users/delete_user_by_id.rs:122-123`, `authorities/delete_authority.rs:149-150`) that describe a nonexistent FK-violation arm should be corrected to reference the audit log instead; the mock tests themselves are unaffected.
4. **Roll the same fix across roles and permissions deletes** (`delete_role`, `delete_permission`: `fetch_optional` + typed not-found + cascade counts for `*_grants` tables) so the four destructive endpoints share one policy; relax `roles/delete_role/mod.rs:55-67` accordingly.
5. **Explicitly rejected alternatives, recorded so they aren't re-litigated:** (a) schema-wide RESTRICT — needs an `ALTER` per FK (all seven), a pre-cleanup pass, converts every delete into a multi-endpoint dance, and deletes exactly the sessions/logout behavior that must stay automatic; (b) staged two-phase delete (`?dry_run=1` preview, or soft-delete tombstone) — the tombstone collides with every read path and the status machine in OXA-000009's area; both are product-sized design tickets, not this bug fix; (c) silently succeeding on repeat deletes — breaks the payload contract (§Analysis chain) and hides the first delete's genuine 403/500 retry distinction. Release note required: `DELETE` on an absent id changes 400 → 404 (status-code-visible change).
