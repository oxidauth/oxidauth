## Problem

The query claims to return "the most recent private key" but its ordering is only a **partial order**: `created_at` has no uniqueness constraint (migration has no index or constraint on it), and several rows can share the identical timestamp. When they do, Postgres is free to return *any* tied row, and which one it returns depends on the physical row order / plan (seq-scan short-circuit vs top-N heapsort vs a hypothetical future index on `created_at`) — things that change with `VACUUM`, page reclamation, ANALYZE stats, and *which replica* runs the query. The result can flip between two calls without a single write.

The tie is not hypothetical because of `NOW()` semantics: any multi-key write batch executed in one transaction (operator rotation script, `psql -1` / `BEGIN; … COMMIT;` seed, single-transaction restore that re-seeds keys via the column default, or a future bulk-rotation service following the `insert_totp_secrets` transaction pattern) stamps every row with the same `created_at` by construction. The pinned test itself reproduces the tie with two rows explicitly seeded at the same timestamp (`mod.rs:109-111`).

What exists in the codebase today:
1. `create_public_key` HTTP call → one auto-commit INSERT → distinct `now()` per key *usually*; ties between concurrent app requests require two transactions starting in the same microsecond tick (theoretically possible, practically rare).
2. Out-of-band SQL batches (rotation scripts, seeds, restores) → guaranteed ties inside the transaction.
3. Test fixtures / explicit-timestamp INSERTs → trivially equal `created_at` (exactly how the pin test builds the tie).

## Analysis

**The NOW()-per-transaction claim is confirmed in code, not just Postgres lore.** `insert_public_key.sql:4` writes `NOW(), NOW()`; the table defaults are `CURRENT_TIMESTAMP` (`20221021180809_create_public_keys.sql:5-6`). Postgres defines both as the transaction start timestamp, fixed for the transaction's duration — this is the documented reason concurrent/serializable transactions can carry overlapping timestamps. So a same-transaction batch has *zero* ordering information in `created_at`.

**Can same-tx key batches exist in practice?** Verified: **not through the current application**. There is no rotation endpoint; `create_public_key` inserts exactly one row per request, auto-committed (so each gets its own transaction-start `now()`); bootstrap creates a single key only when the table is empty; `oxidauth-import-export` contains no `public_keys` handling (grep: no matches). The realistic tie sources are: (a) operator/DBA rotation or seeding scripts wrapping multiple INSERTs in one transaction — the register's scenario, still entirely plausible for an auth server whose only in-app rotation primitive is "POST another key and let `ORDER BY` sort it out"; (b) single-transaction restores/seeds that rely on the column `DEFAULT` rather than dumped timestamps; (c) any explicit-timestamp INSERTs with equal values; (d) a future batch-rotation repository following the in-repo `insert_totp_secrets` transaction precedent.

**Why this is more than cosmetic — the delete interaction.** Verification tolerates *any* signer **as long as every tied key stays in the table**: `decode_with_public_keys` (`jwt/mod.rs:68-81`) tries each served key, and tokens carry no `kid` (`Header::new`, `jwt/mod.rs:54`). The knife-edge is `DELETE /api/v1/public_keys/{id}` (route: `oxidauth-api/src/server/api/v1/public_keys/mod.rs:18`). After a tied rotation batch, the operator has no way to see which key is actually signing (no `kid` on any issued token), so post-rotation cleanup is a coin flip: delete the row that *wasn't* supposed to be chosen but *was* — every token signed with it fails verification instantly, mid-TTL, for all live sessions. That converts "arbitrary row order" into a mass-401 outage triggered by routine key hygiene.

**Rotation intent silently fails even without deletion.** A rotation batch that inserts a new key in the same transaction as, say, a companion key (or with a seed that inserts two candidates) may keep signing with a row the operator considers superseded; and because the winner can differ per plan/statistics across the primary and each read replica (`READ_DATABASE_URL`, `lib.rs:9-10`), different app instances can silently sign with *different* keys from the same data. Debugging "why did this token fail after the key cleanup" is then impossible from the outside — nothing in the token identifies its signer.

**Wrong tie-breaker to reach for:** `updated_at`. The sibling guard test asserts `updated_at` must **not** drive ordering (`mod.rs:84-86, 95`: the `mid` row has the newest `updated_at` and must lose), and correctly so — `updated_at` is mutable by unrelated UPDATEs and says nothing about key freshness.

**Edge cases:**
- Empty table → `fetch_one` → `sqlx::Error::RowNotFound` (pinned by `it_should_error_when_no_keys_exist`, `mod.rs:65-78`); any fix must keep `LIMIT 1` returning exactly one row or `RowNotFound`, and that pinned behavior stays untouched.
- A future `CREATE INDEX ON public_keys (created_at DESC)` would *change* tie resolution without any code edit — determinism must come from the `ORDER BY` itself, not from hoping the plan stays stable.
- `ctid`- or `xmin`-based tie-breakers must be rejected: physical tuple order is not stable across VACUUM/page reuse, and `xmin` wraps/freezes — same class of nondeterminism.
- Ties already in production data won't be repaired by the query fix alone; they only become *deterministic* (see audit below).

**Related register items (cross-refs, not duplicates):** DATA-9 (`LIMIT 1` without `ORDER BY` elsewhere — same "arbitrary row" class), DATA-13 (no `ORDER BY` in `select_all_public_keys` — jwks/listing order), DATA-4 (no uniqueness in `public_keys` — duplicate key material compounds "which key is really signing" forensics), SEC-11 (different defect, same `jwt/mod.rs` file). The missing `kid` header is *adjacent hardening* tracked nowhere as its own item yet — noted under Proposed resolution §4.

## Impact

- **Who can hit it:** operators rotating keys via SQL scripts or restores (the register's scenario), anyone seeding `public_keys` with equal timestamps, and any deployment that later grows a bulk-rotation path following the in-repo transaction precedent. Every API end user is downstream: all JWTs (login, register, refresh, TOTP) are signed with the key this query picks.
- **Severity rationale (P2 as registered):** the defect is silent key nondeterminism, not an immediate break. The realistic worst case is **availability of all live sessions** — deleting the "wrong" tied key during post-rotation cleanup invalidates every token signed with it instantly, and the missing `kid` means the cleanup decision is made blind. If you assume unqualified SQL access by hostile actors this rises (they can *create* the tie), but so can they do far worse with SQL write access; P2 with the delete-cleanup path is the honest rating.
- **Data/integrity:** a "rotated" key may never actually sign anything (batch tie picks the other row) while the operator believes rotation completed — audit/compliance expectation of key freshness is silently unmet. Multi-replica setups can sign with mixed keys, undetectable because tokens carry no key id.
- **Observability:** failure mode is "some old tokens suddenly 401 after key cleanup" or "two instances disagree" — nothing points at `ORDER BY`.
- **No confidentiality impact:** the private half is never served by any endpoint; verification-side consumers are unaffected by the tie (they try all keys regardless of listing order).

## Proposed resolution

**1. Add a total-order tie-breaker to the SELECT (minimum fix).** `oxidauth-postgres/src/private_keys/select_most_recent_private_key/select_most_recent_private_key.sql`:

```sql
SELECT
    id,
    private_key,
    created_at,
    updated_at
FROM public_keys
ORDER BY created_at DESC, id DESC
LIMIT 1
```

Postgres compares `UUID` byte-wise (memcmp over the 16 bytes), and Rust's `Uuid: Ord` uses the same byte order, so the expected winner is expressible in tests on both sides. `created_at` is `NOT NULL`, so no `NULLS LAST` clause is needed. This makes the pick **deterministic and plan-independent** — the remaining arbitrariness ("largest random UUID among ties, not the intended one") is fixed by step 2 for all future app writes and by the step 3 audit for legacy rows. No migration required for this step; the `LIMIT 1`/`RowNotFound` contract pinned at `mod.rs:65-78` is unchanged.

**2. Make app writes self-ordering: `NOW()` → `statement_timestamp()` (recommended companion).** `oxidauth-postgres/src/public_keys/insert_public_key/insert_public_key.sql:4`:

```sql
VALUES (COALESCE($1, uuid_generate_v4()), $2, $3, statement_timestamp(), statement_timestamp())
```

`statement_timestamp()` is the current *statement's* start time — distinct per INSERT even inside one explicit transaction — so any future/app-side same-tx rotation batch gets strictly increasing `created_at` and the semantically-newest key wins **by `created_at` alone**, exactly as `ORDER BY created_at DESC` intends. `RETURNING *` response shape is unchanged (still `timestamptz`), `insert_public_key/mod.rs` needs no change, and out-of-band ties (column `DEFAULT CURRENT_TIMESTAMP` seeds) degrade to the deterministic id tie-break from step 1.

**3. Data-hygiene audit for existing ties (report-only migration).** Follow the repo's migration naming, e.g. `oxidauth-postgres/migrations/<ts>_audit_public_keys_created_at_ties.sql`:

```sql
-- report only: rows sharing a created_at (deterministic pick now = max id,
-- but operators should decide which key actually signs)
CREATE OR REPLACE FUNCTION public_keys_audit_created_at_ties()
RETURNS TABLE (created_at TIMESTAMPTZ, key_count BIGINT, ids UUID[]) AS $$
  SELECT created_at, count(*), array_agg(id ORDER BY id)
  FROM public_keys
  GROUP BY created_at
  HAVING count(*) > 1;
$$ LANGUAGE sql;
SELECT * FROM public_keys_audit_created_at_ties();
```

Report never auto-fixes (which tied key should sign is an operator decision): either `DELETE /api/v1/public_keys/{id}` the unintended row, or desynchronize timestamps (`UPDATE public_keys SET created_at = created_at - (rn * interval '1 millisecond') FROM (SELECT id, row_number() OVER (ORDER BY id) rn FROM public_keys WHERE created_at = '<tie stamp>') t WHERE t.id = public_keys.id`). Safe to replay; SELECT/function-definition only.

**4. Optional hardening (separate ticket, do not bundle):** populate `kid` in `Jwt::encode` (`oxidauth-kernel/src/jwt/mod.rs:54`, e.g. `Header` with `kid = Some(key id)`) and expose it in the jwks listing, so verifiers stop brute-forcing all keys and operators can see *which* key signed any live token before deleting one. This removes the blind-cleanup hazard that turns this bug into an outage; it is a wire-format change (client-visible claim-header addition) and deserves its own compat review (the `oxidauth-rs` client's `decode_with_public_keys` path keeps working either way, but downstream verifiers may parse headers).

**5. Optional full-semantics variant instead of steps 1+2:** add `seq BIGINT GENERATED ALWAYS AS IDENTITY` to `public_keys` and order `created_at DESC, seq DESC` — insertion order even for default-timestamp seeds. Costs a migration plus the `FromRow` mappings (`oxidauth-postgres/src/public_keys/mod.rs`, `private_keys/mod.rs:20-26` `PgPrivateKey`) and every `SELECT` column list; the historical tie backfill inherits heap order, which *is* insertion order for append-only tables but is an assumption. Not recommended as the first move; steps 1+2 are zero-migration and cover every path the code can execute.

**6. No index needed** — the table holds a handful of rows (one keypair per rotation, deletions via API); `ORDER BY … LIMIT 1` over it is already trivial. If it ever grows, `CREATE INDEX ON public_keys (created_at DESC, id DESC)` then.

**Pin flips (only `BUG(pinned)` marker for this item is `select_most_recent_private_key/mod.rs:105-108`):**
- `it_should_pin_the_same_created_at_tie_as_unspecified` (`mod.rs:103-124`): delete the `BUG(pinned)` comment (`:105-108`), rename to `it_should_deterministically_break_same_created_at_ties`, and replace the disjunctive assertion at `:118-121` (`winner.id == first || winner.id == second`) with the exact expected id under the new rule: `assert_eq!(winner.id, std::cmp::max(first, second), "ties must break to the greater id")` plus `assert_ne!(winner.id, std::cmp::min(first, second))`. The seed ids are `Uuid::new_v4()` (`:49`) and the created_at values are equal by design (`:109-111`), so this pins the total order without touching the seed helper. (If the §5 identity-column variant is chosen instead, the expectation flips to "the row inserted last in the seed order".)
- The two neighboring tests are invariants, **not** pins — keep unchanged: `it_should_error_when_no_keys_exist` (`:65-78`, empty-table `RowNotFound`) and `it_should_pick_the_newest_created_at_regardless_of_insert_order` (`:80-101`, `updated_at` must not order — the reason the tie-breaker is `id`/`seq`, never `updated_at`).
- Add one regression test for the writer fix: seed two keys through `PgPublicKeyRepository::call` (real `insert_public_key.sql`) from inside a single `pool.begin()` transaction using the raw query against `&mut tx` (mirroring `totp_secrets/insert_totp_secrets/mod.rs:19-30`), commit, then assert `select_most_recent_private_key` returns the **second** inserted key — before `statement_timestamp()` this test is a coin flip (both rows share the tx-start `now()`); after it, it passes deterministically.

**Compat/migration concerns:** none for steps 1-2 — no schema change, no response-shape change (`RETURNING *` still `timestamptz`), no API contract touched; the only observable shift is *which* row wins on a previously-ambiguous tie (from arbitrary to max-id, and to true insertion order for app writes going forward). `oxidauth-import-export` does not touch `public_keys` (verified). The `oxidauth-rs` client is unaffected (it never sees the private key and its verification iterates all public keys).
