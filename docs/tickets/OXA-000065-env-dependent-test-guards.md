## Problem

Register T-5 reads: *"Env-touching tests must use each crate's serial guard (`oxidauth-services` `ENV_LOCK` + `env` accessors; `oxidauth-api` `GLOBAL_LOG` for `tracing::subscriber::with_default`) — global subscriber/env races otherwise."* A code audit shows the convention is real and enforced in `oxidauth-services` / `telemetry` / `postgres`, but the register text is partly fictional and the enforcement has one hole:

1. **`oxidauth-api` `GLOBAL_LOG` does not exist.** Repo-wide grep: zero hits for `GLOBAL_LOG` (tree and `git log --all -S GLOBAL_LOG`), zero `tracing::subscriber::with_default` / `set_default_reader` usages, and `oxidauth-api`'s three test mods (`middleware/permission_extractor.rs:79`, `middleware/can.rs:84`, `server/api/v1/auth/oauth2/callback.rs:150`) touch neither env nor the subscriber. The clause names a guard for tests that were never written — it is forward-looking guidance masquerading as a record. Meanwhile it **omits the two guards that do exist** (`telemetry`, `postgres`), each an independently defined `ENV_LOCK`.
2. **One real bypass (latent flake).** `bootstrap::tests::a_failing_create_step_aborts_before_later_steps_and_saves_nothing` (:1619) runs bootstrap with `Cfg { create_fails: true, ..ALL_ABSENT }` (:1621-1627): the authority mock is `State::Miss` (:734, :1029-1036), so the create branch `first_or_create_authority` executes `env::var(DEFAULT_CLIENT_KEY)` (:397) — a process-global env **read** that does **not** hold `ENV_LOCK`. Four sibling tests concurrently `set_var`/`remove_var` that exact key under the lock (`EnvBatch::apply` :1346-1348). The read is outside the invariant stated verbatim in the code's SAFETY comments ("every test … that mutates or (via product code) reads the process environment does so while holding `ENV_LOCK`", :649-650), so it is the unguarded half of the edition-2024 `set_var`/`get_var` race. It has not *flaked* because (a) the assertion set (:1644-1655) never inspects the authority payload and (b) the interleaving window is tiny — this is a UB-grade race, not (yet) an assertion failure. The two recorded full audits (missing-tests.md :553, :627) missed it.
3. **The convention lives only in code comments.** No `CONTRIBUTING.md` and no testing-conventions doc exists (`docs/` has none; `README.md`/`docs/*.md` never mention `ENV_LOCK`). Every new env-touching test — and the pending fix tickets below will add several — relearns the rule by spelunking, and nothing prevents a second bypass.

## Analysis

**Guard mechanics (verified, all three are the same design):** plain `std::sync::Mutex<()>`, poison-tolerant acquisition `unwrap_or_else(|p| p.into_inner())` — a panicking test poisons the mutex but its `Drop` has already restored env during unwind, so recovery via `into_inner` is sound and keeps the rest of the suite from lock-failing in cascade.

- `oxidauth-services` `ENV_LOCK` (lib.rs:36) is `#[cfg(test)]`-gated — correct, because production env reads all happen on single-threaded startup paths (`main.rs` before the server starts; bootstrap during boot), never concurrently with mutation; the hazard is purely intra-test-process. `EnvGuard::set/unset` capture the previous value and restore it in `Drop`, releasing the lock only after the restore (field drop order, comment :85-87). Multi-var needs use `EnvBatch` (bootstrap/mod.rs:634-673): **one** acquisition, reverse-order restore while still holding the lock — because `ENV_LOCK` is **non-reentrant**, two per-var guards in one test self-deadlock (a real historical failure, missing-tests.md :555; fixed via `EnvBatch`, :627).
- `telemetry` (lib.rs:103) and `postgres` (lib.rs:331) each define their own `LazyLock<Mutex<()>>` + `env_guard()`; tests hold it for the full test body. Unlike `EnvGuard` they do **not** save/restore prior values (manual `remove_var` cleanup, :180/:187/:201/:208; postgres :477/:508). Safe in practice: postgres keys are `TEST_`-prefixed and can never collide with the real `.env` (comment :304-306), and no other test in either binary reads those keys — but it is an asymmetry worth recording.
- Enforcement census in `oxidauth-services`: **36 guarded acquisitions** — 31 `EnvGuard::set/unset` (authenticator.rs ×2, update_password.rs ×2, registrar.rs ×2, auth/register.rs ×3, auth/authenticate.rs ×10, create_user_authority.rs ×5, authorities register.rs ×1, authorities authenticate.rs ×6), 1 direct `ENV_LOCK.lock()` (authorities authenticate.rs:209-211, the env-absent precondition), 4 `EnvBatch::apply`. Spot-checked every *unguarded* test in those mods: each short-circuits before any env read (e.g. `unknown_client_key…` auth/authenticate.rs:900, `single_use_token…` :918, `missing_database_url` display tests) — **except** the bootstrap bypass above. `telemetry`: all 6 env tests guarded; the two direct `unsafe set_var` (:180, :201) sit inside guarded tests; the two remaining tests construct `EnvVarError` values without env access. `postgres`: all 4 env tests guarded; `lazy_pool()` deliberately uses `NEVER_CONNECTS_URL` (:328, :353-359), never env, so env-removal tests and pool tests cannot interfere.

**Why env needs a lock at all:** the process environment is a single process-global block; `std::env::set_var`/`remove_var` became `unsafe` in **edition 2024** (verified: `edition = "2024"` in all three crates' `Cargo.toml`:4) precisely because they race with concurrent `get_var` reads. Cargo's libtest harness runs one binary with many threads by default, and `#[tokio::test]` adds multi-thread worker threads that execute the product `env::var` calls — the guard still covers them because the `MutexGuard` is held on the test thread across the `.await` points. There is **no rayon** anywhere in the workspace (grep: zero), so libtest + tokio are the complete concurrency sources. Different crates are different test binaries = different processes, which is why each crate keeping its own `ENV_LOCK` is correct, not duplication.

**The subscriber half of T-5 (currently moot, will not stay moot):** `telemetry::init_subscriber` :48-50 calls `tracing::subscriber::set_global_default`, which can succeed once per process and panics (`.expect`) on a second call — any test calling it poisons every later caller. The safe pattern is scoped `tracing::subscriber::with_default` + the crate's serial lock (that is the guard shape "GLOBAL_LOG" names). Also `get_subscriber` :27 calls `EnvFilter::try_from_default_env()` — i.e. **building a subscriber is itself an unguarded `RUST_LOG` read**, so the day a ticket adds subscriber tests (OXA-000046 is the natural candidate — its pinned `EnvVarError::RustLog` test needs a capturing subscriber) they are automatically env-touching tests. No test does any of this today.

## Impact

- **Today:** one latent data race (bootstrap :1619), no observed flakes; no cross-crate impact (separate processes). Every guard-covered test is deterministic in parallel runs — which is exactly what keeps T-8 honest (no `-- --test-threads=1` needed).
- **Convention drift:** undocumented rules don't survive; the self-deadlock class (non-reentrant lock, two guards) and the multi-var case (needs `EnvBatch`, which is currently *private to the bootstrap test mod* :634, not reusable elsewhere) are precisely the traps a new contributor hits blind.
- **Register integrity:** T-5 as written misdirects a fixer toward a nonexistent `GLOBAL_LOG` and away from the two real xlib guards; leaving it uncorrected guarantees wasted investigation.

## Proposed resolution

**Disposition: KEEP the convention (it is load-bearing and working) + codify + fix the one bypass + correct the register text.**

1. **Fix the bypass:** wrap the `bootstrap::tests::a_failing_create_step…` body in `EnvBatch::apply(&[(DEFAULT_CLIENT_KEY, None), (DEFAULT_ADMIN_PASSWORD, None)])` (deterministic absent-env pin, matching the :1463 test's pattern) — or at minimum `crate::ENV_LOCK` direct-lock the test. While there, promote `EnvBatch` from `bootstrap/mod.rs` test mod (private :634) to `lib.rs` next to `EnvGuard` so the deadlock-safe multi-var guard is reusable — the bootstrap/B4 slices have already proven every multi-var test needs exactly one acquisition.
2. **Reword register T-5** to the audited truth: per-crate test-only `ENV_LOCK` (`std::sync::Mutex<()>`, poison-tolerant) in `oxidauth-services` (+ `EnvGuard` set/unset restore, `EnvBatch` for multi-var — one acquisition, non-reentrant lock), `telemetry`, and `postgres`; invariant = *any test that mutates env or reaches product env reads (directly or through product code) holds the lock for its whole body*; subscriber guidance (`init_subscriber` is once-per-process; tests use `tracing::subscriber::with_default` under the same kind of lock — and note `get_subscriber` reads `RUST_LOG` via `try_from_default_env`, so subscriber tests are env tests).
3. **Codify outside the register:** add a "Testing conventions → environment & global subscribers" section (new `CONTRIBUTING.md`, or fold into `docs/` alongside the T-6 postgres conventions): the invariant, which guard to reach for per crate, the one-acquisition rule, restore semantics, and the edition-2024 `unsafe` rationale. Resolution of this ticket = the doc change that makes the rule discoverable.
4. **Pending tickets that inherit this convention** (their fixes will add exactly the env-touching tests this rule governs): **OXA-000038** (bootstrap boot-path — new bootstrap tests live in the very mod with the bypass and must use `EnvBatch`/`EnvGuard`); **OXA-000008** (password serialization — regression tests around the username_password hashing paths exercise `Authenticator::new`/`Registrar::new`, which read `OXIDAUTH_USERNAME_PASSWORD_PEPPER`, authenticator.rs:73 / registrar.rs:73); OXA-000046 (telemetry `RustLog` pinned error — any subscriber-capturing test there is the first real user of the subscriber clause). Sibling tooling tickets: OXA-000061/000062 (T-1/T-2); interplay with T-8 (parallel safety is *because of* these guards).

## Verification

No behavior change for guard-covered tests; verification is that the guarded suites stay green in parallel (the guards only serialize the env-touching subset) and that the bypass fix restores the textual invariant:

```
cargo test -p oxidauth-services --lib bootstrap::           # guarded bootstrap suite incl. the fixed bypass test
cargo test -p oxidauth-services --lib auth                  # the pepper-guarded auth/user-authority tests (24 EnvGuard sites)
cargo test -p oxidauth-services --lib authorities::strategies::username_password
cargo test -p telemetry --lib                               # all 8 telemetry tests
cargo test -p postgres --lib db_tests                       # guarded from_env/migrate-flag env tests
```

The race itself is probabilistic — green runs never proved its absence, which is why the fix is structural. Post-fix acceptance check (audit, not execution): `grep -rn "env::var\|set_var\|remove_var" src/oxidauth/oxidauth-services/src` — every site must sit inside `lib.rs`'s `EnvGuard`, `EnvBatch`, or a test holding `ENV_LOCK` (the direct-lock test at authorities authenticate.rs:209 being the sanctioned pattern); repeat the same one-liner over `src/xlib/telemetry/src` and `src/xlib/postgres/src`. A stress probe (`cargo test -p oxidauth-services --lib bootstrap -- --test-threads=8`, repeated) may be run for confidence but is not proof either way.
