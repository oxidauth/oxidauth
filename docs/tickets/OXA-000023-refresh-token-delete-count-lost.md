## Problem

The query deletes every row matching `WHERE user_id = $1` — an unbounded, user-scoped bulk operation — but the executor treats it as a single-row lookup:

1. **Count lost.** With N ≥ 1 matching rows, `fetch_one` (`mod.rs:19`) returns the *first* `RETURNING` row and silently drops rows 2..N. The service response (`Response = RefreshToken`, `mod.rs:8`) can carry at most one id, so a caller that wants to log, audit, or return "how many sessions were revoked" cannot compute it from the response — the information is destroyed between the database and the caller. The pinned test demonstrates the absurdity: after two deleted rows, the test can only assert the response `id` is *one of the two* (`mod.rs:66-70`).
2. **Zero rows is an error.** With N = 0 — the *normal state* for a user whose sessions all expired or who never logged in — `fetch_one` yields `sqlx::Error::RowNotFound`, and because `Response = RefreshToken` is non-optional there is no "deleted nothing" channel. `forgot_password` propagates it via `?` (`forgot_password.rs:76`), and the handler turns it into HTTP 400 (`api/.../forgot_password.rs:27`). Result: **a user with a valid TOTP secret and zero live refresh tokens cannot use the forgot-password flow at all** — pinned as intended-green by `it_should_error_when_the_user_has_no_tokens` (`mod.rs:84-104`).

Which single row survives the truncation in case (1) is not contractual: with multiple matches the answer depends on scan order/plan (the `refresh_tokens_user_id` index may or may not be consulted for the DELETE), i.e., the same plan-luck class as register DATA-9/DATA-13 (OXA-000022, OXA-000019). [INFERENCE — mechanism analysis; no test exercises multi-row ordering here, and the pinned test deliberately asserts the disjunction.]

## Analysis

**The DELETE itself has always been correct and unconditional.** The pinned test verifies all of alice's rows are gone (`token_count == 0`) in both the N ≥ 1 and N = 0 cases — `fetch_one` truncates the *result set*, not the delete. The defect is purely in the response shape: it simultaneously (a) under-reports for N > 1 and (b) fails outright for N = 0, which is a strict subset of "under-reports."

**The zero-row error is the only today-observable harm, and it lands on real users.** Flow for a forgot-password request: fetch TOTP secret → generate code (`forgot_password.rs:55-68`) → bulk delete tokens → return code. A zero-token user therefore does everything right and still gets 400 `"database row not found"` — indistinguishable on the wire from a malformed request (same `Err` arm, `:27`). Ordering quirk: the error fires *after* a valid code was generated and discarded, and the 200-vs-400 split leaks whether a user currently holds refresh tokens — a second oracle on top of the existence/TOTP-enrollment oracle OXA-000005 already documents (marginal, but it evaporates with this fix). Note this functional bug is listed in OXA-000005's problem statement but its *fix* lives here: no matter how revocation timing is redesigned, the query must stop erroring on zero rows and must report a count.

**Nobody benefits from the current shape; the one caller discards the row.** `forgot_password` ignores the `RefreshToken` value (`forgot_password.rs:76`), so today the single-row response has exactly zero consumers while imposing the RowNotFound failure mode on the only call site. The shape exists because the module was template-copied from the by-id delete (which legitimately returns one row) without adjusting for cardinality — the same copy-paste lineage OXA-000020 traces across all `delete_*` modules.

**Why `Vec<RefreshToken>`, not `usize`, and why it's safe.** (a) The `refresh_tokens` table stores **no secret material** — columns are `id, user_id, authority_id, expires_at, created_at, updated_at` (`migrations/20221027183328_create_refresh_tokens.sql:1-11`; `PgRefreshToken` maps exactly these, `refresh_tokens/mod.rs:23-30`), so returning every deleted row leaks nothing beyond session metadata. (b) `fetch_all` is the established convention for plural queries in this crate (all `select_all_*` / `select_*_by_user_id` modules, grep-verified). (c) A `Vec` subsumes the count (`len()`) *and* preserves which sessions died (ids + authorities + expiry) for future audit logging — OXA-000020's central complaint about user/authority deletes is exactly "the collateral is unrecordable", and here we get the record for free. (d) Row count per user is naturally tiny (active sessions under `refresh_token_ttl`), so the fetch-all cost is nil. A `usize`-via-`execute()`-`rows_affected()` variant was considered and rejected in step 3 below.

**Dead trait to clean up.** `DeleteRefreshTokenByUserIdServiceTrait` / `DeleteRefreshTokenByUserIdService` (`oxidauth-kernel/.../delete_refresh_token_by_user_id.rs:11-19`) duplicate the query signature in a service-trait pattern nothing in the workspace uses for this operation (unlike `ForgotPasswordServiceTrait`, they have no impl and no `Arc` consumer). Under clean cutover they should be deleted with this change rather than carried forward to a second signature update; if the repo intends to adopt the pattern crate-wide later, restoring them is one `git revert`.

**Severity (P3 as registered, agreed).** The count-loss is pure API hygiene today (no consumer wanted the count). The zero-token 400 is a real user-facing failure but confined to the forgot-password endpoint for users who happen to hold zero refresh tokens (a transient, recoverable state — any login ends it), and the flow is itself pending redesign in OXA-000005. No data corruption; the DELETE is always correct. P3 is the honest grade.

## Impact

- **Who is affected today:** any user with a registered TOTP secret and zero live refresh tokens — logged out everywhere, sessions expired, or enrolled-but-never-logged-in — receives HTTP 400 from `POST /v1/auth/username_password/forgot_password` and cannot reset their password through the public flow until they obtain a session some other way. The state is common enough to matter (refresh tokens expire per the authority's `refresh_token_ttl`), and the error text points at "database row not found", sending operators hunting for data problems.
- **Who is affected prospectively:** OXA-000005's resolution moves counted revocation into `update_password` ("revoke on actual password change") and wants a revocation count for the response/log; OXA-000020's cascade-visibility fix would like the same for user deletes. Both are blocked on this query (or its successor) returning a count.
- **Observability today:** nothing logs how many tokens a forgot-password call killed (`tracing::instrument` at `mod.rs:10` records only `user_id`); security-relevant bulk revocations are uncountable after the fact.
- **Not affected:** the DELETE's correctness (always full scope, verified by pins); `delete_refresh_token_by_id` (single-row semantics are right); every other endpoint; the wire shape of any API (no endpoint returns the deleted rows — see Resolution §compat).

## Proposed resolution

**1. `fetch_all` → `Response = Vec<RefreshToken>` with empty-vec-on-nothing semantics (the whole fix is type-level).** Call-site diffs:

- `oxidauth-postgres/src/refresh_tokens/delete_refresh_token_by_user_id/mod.rs`:
  ```rust
  type Response = Vec<RefreshToken>;                                    // :8

  async fn call(&self, params: &'a DeleteRefreshTokenByUserId)
      -> Result<Vec<RefreshToken>, BoxedError> {                        // :11-14
      let result = sqlx::query_as::<_, PgRefreshToken>(include_str!(
          "./delete_refresh_token_by_user_id.sql"
      ))
      .bind(params.user_id)
      .fetch_all(&self.db.write_pool())                                 // :19  fetch_one → fetch_all
      .await?;

      Ok(result.into_iter().map(RefreshToken::from).collect())          // replaces :22-24
  }
  ```
  Add a doc-comment on the impl stating the contract: *"Deletes every refresh token of `user_id`. Returns the deleted rows (possibly empty); zero matches is a success with an empty Vec, never an error."* Optionally `tracing::info!(count = deleted.len())` (or `.record("deleted_count", …)` on the existing instrument at `:10`) — cheap security observability, no behavior change.
- `oxidauth-repository/src/refresh_tokens/delete_refresh_token_by_user_id.rs:8-15`: `Response = Vec<RefreshToken>` in both the supertrait bound and the blanket `impl<T>` bound.
- `oxidauth-kernel/src/refresh_tokens/delete_refresh_token_by_user_id.rs`: **delete `DeleteRefreshTokenByUserIdServiceTrait` and the alias (`:11-19`, dead — see Locations)**, keeping the `DeleteRefreshTokenByUserId` DTO and re-exports. (Fallback if maintainers want the trait kept: change `:16` to `Result<Vec<RefreshToken>, BoxedError>` — do not do both.)
- `oxidauth-services/src/auth/strategies/username_password/forgot_password.rs`: **product code unchanged** — `:76` already discards the value; it simply stops being able to receive `RowNotFound` from this call. Test mock `MockDeleteRefreshTokens` (`:165-191`): `type Response = Vec<RefreshToken>` (`:167`) and `Ok(vec![RefreshToken { … }])` (`:183-190`) — returning a one-element vec keeps it representative; the three use-case tests (`:236`, `:268`, `:289`) assert only call-log contents and stay green.
- Naming decision: keep `DeleteRefreshTokenByUserId` / `delete_refresh_token_by_user_id` (the name describes the *scope*, and the by-id sibling's existence makes the singular "Token" ambiguous-but-parallel). No rename — unlike DATA-11's lying predicate, this name is not false; the doc-comment from step 1 carries the plural semantics. Renaming would ripple through five crates for cosmetics.

**2. Why empty vec, not `Option`/error.** Bulk delete-revoke is idempotent by nature: deleting from an empty set *is* success. `Option<RefreshToken>` would keep the count-loss for N > 1 while fixing only N = 0 — the wrong half. `Response = Vec<…>` makes N = 0, 1, N one code path. This matches the idempotency direction OXA-000020 §Analysis reaches for user/authority deletes (where it is blocked by DTO/client-contract churn; here there is none, so take it now).

**3. Rejected alternatives:**
- *`usize` via `sqlx::query(...).execute()` + `rows_affected()`:* smallest payload, and OXA-000005 listed it as an option ("fetch_all/EXECUTE-with-count"), but it discards *which* sessions died, diverges from the `delete_*`-returns-rows convention used by every sibling module, and `rows_affected` for `DELETE … RETURNING` is a sqlx behavior detail worth not depending on. `Vec::len()` gives the identical count. Rejected.
- *Keep `fetch_one` and count in a second statement (`DELETE` + `SELECT COUNT(*)` wrapped in a transaction):* more code, a race window, strictly less information. Rejected.
- *Change the SQL to `DELETE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` for row-certain reporting:* unnecessary — `RETURNING` is already atomic per statement; concurrency between two concurrent bulk deletes for the same user just splits the rows between the two result vecs, which is the truthful answer. No SQL change beyond keeping `RETURNING *`; the file stays as-is.

**4. Pin flips (the only marker is `mod.rs:58-60`):**
- `it_should_delete_only_the_target_users_tokens` (`mod.rs:49-81`): delete the `BUG(pinned)` block (`:58-60`); replace the single-row assertions (`:66-70`) with `assert_eq!(deleted.len(), 2)`, `assert!(deleted.iter().all(|t| t.user_id == alice))`, and a set assertion `{deleted[0].id, deleted[1].id} == {alice_first, _alice_second}` (sort by id to avoid ordering assumptions — no ORDER BY exists on the delete's RETURNING, per Problem). Keep every bob/DB-state assertion (`:72-80`) unchanged.
- `it_should_error_when_the_user_has_no_tokens` (`mod.rs:84-104`): **the behavior flip proper.** Rename to `it_should_return_an_empty_vec_when_the_user_has_no_tokens`; assert `.await.expect("empty bulk delete must succeed").is_empty()` plus the existing bob-survives check (`:103`). Before the fix this test fails exactly where it should (`RowNotFound`); after, green.
- forgot_password.rs mock (`:167`, `:183-190`): type change only; all three use-case tests (`returns_a_fresh_totp_code_and_revokes_the_users_refresh_tokens` `:236`, `totp_secret_lookup_failure_propagates_without_deleting_tokens` `:268`, `refresh_token_delete_failure_propagates` `:289`) stay green — the `fail: true` mock arm still exercises error propagation.
- Once green: remove the `DATA-10` row at `BUGS_AND_NOTES.md:42`; add a bullet to the OXA-000005 resolution noting the query now reports counts (its "revocation accounting needs …" prerequisite is met).

**5. Compat.** No HTTP/DTO/wire change: no endpoint exposes deleted rows, `oxidauth-http` has no forgot-password response DTO carrying them, no `oxidauth-rs` wrapper or hurl test covers this operation (verified above). The trait signature change is workspace-internal: `oxidauth-repository` traits are implemented only by `oxidauth-postgres` and mocked in `oxidauth-services` tests (all in-tree, all covered by steps 1/4). The **one consumer-visible behavior delta**: `POST /forgot_password` for a zero-token user flips 400 → 200 + code — a strict bug fix, but flag it in the changelog since integrators may have (accidentally) treated the 400 as "user has no sessions". The kernel service-trait deletion breaks nothing (dead code, verified); out-of-tree implementers of `DeleteRefreshTokenByUserIdQuery` (if any exist beyond this workspace) must update their `Response` — standard semver-major signal for a published crate.
